# ARCHITECTURE — MasterHand

Technical design. For scope and requirements see `SPEC.md`; for status see `PROGRESS.md`.

## 1. Overview

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Web         │  │  Desktop     │  │  Mobile      │
│  React 19    │  │  Electron    │  │  React Native│
│  + Vite      │  │  (web build) │  │  (Expo)      │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       │                 │                 │
       └─────────────────┼─────────────────┘
                         │ HTTPS — TLS provided by the deployer
                         │ (Caddy / Nginx / Traefik / tunnel / ...)
                  ┌──────▼───────┐
                  │  MasterHand  │  Node 22 + Hono — apps/server
                  │  BFF         │  · login: signed cookie (web) / token (native)
                  │              │  · proxy /api/oc/* → opencode (injects basic auth)
                  │              │  · SSE relay /api/events
                  │              │  · SQLite (devices/tokens)
                  └────┬─────────┘
                       │ SSE /api/event (permanent connection)
                       ▼
                  ┌──────────────┐
                  │ opencode     │  4096 (internal network only)
                  │ serve        │  OPENCODE_SERVER_PASSWORD
                  └──────┬───────┘
                         ▼
             Model providers · agents · MCP servers
```

> In production the BFF and opencode run as Docker containers orchestrated with Compose (see §6). TLS termination is **not** part of this repository.

**Guiding principle:** clients never talk to opencode directly. The BFF is the only bridge; it centralizes security and exposes a single origin for every platform.

## 3. Stack and rationale

| Layer | Choice | Rationale |
|---|---|---|
| Web UI | React 19 + Vite + TS | Ecosystem, fast iteration |
| Mobile UI | React Native + Expo | One language across platforms, native distribution |
| Desktop | Electron serving the bundled web build | Reuses the whole web UI and lets the app's Servers screen own server selection; no remote origin is trusted with the shell's window |
| Shared logic | `packages/client-core` | One API/query/SSE layer reused by all clients; platform UI stays free. It must run without DOM globals: React Native has no `document` and its global `window` has no DOM listener API, so anything web-specific is feature-detected |
| UI styling | Tailwind v4 mapped to the `design/DESIGN.md` tokens (web/desktop) · RN primitives (mobile) | Mobile-first, no lock-in; one token source for both utilities and the ported component classes, light/dark through `light-dark()` |
| Message rendering | `react-markdown` + `remark-gfm`/`remark-breaks` (web/desktop) · `@ronradtke/react-native-markdown-display` (mobile) | Assistant replies are markdown (tables, lists, code, links); both render React elements with no raw-HTML path |
| API client | `@opencode/client` (v2, Promise) pointed at the BFF proxy | Generated client and types from opencode's v2 contract; the BFF injects auth |
| State | TanStack Query | Event-driven server cache (SSE → `setQueryData`); works on web and React Native |
| BFF | Node 22 + Hono | Lightweight `streamSSE` and proxying |
| Auth | Signed HttpOnly cookie (web) + signed Bearer token (native) | Best fit per platform; single signing secret |
| Persistence | SQLite | Real persistence without extra infrastructure |
| Deploy | Docker Compose | Reproducible, one command; TLS stays with the deployer |

## 4. Main flows

### 4.1 Prompt submission and streaming

1. The client sends `POST /api/oc/api/session/:id/prompt` through the BFF (which adds opencode's basic auth). Model and agent are **not** part of the prompt: when the composer selection differs from the session's remembered `agent`/`model`, the client first calls `POST /api/oc/api/session/:id/agent` and/or `/model` (with the variant inside `Model.Ref`) and only then prompts.
2. opencode admits the input and returns the inbox item; the agent runs.
3. The BFF keeps a permanent SSE connection to opencode's `GET /api/event` (all locations; each frame is one v2 event object) and re-emits it on the BFF's `GET /api/events`.
4. The client renders live streaming from the granular events: `session.text.*` and `session.reasoning.*` deltas (keyed by `assistantMessageID` + `ordinal`, numbered per kind), `session.tool.*` for tool cards and `session.step.ended` for cost/tokens.
5. When the turn ends, opencode emits `session.execution.succeeded` (or `failed`/`interrupted`); the client refetches the projected messages, which replace the live state.
6. While a step is streaming, the projection includes the in-flight assistant message but omits its accumulated text (verified against a live 2.0.21 server); a mid-step refetch therefore merges the live text/reasoning parts instead of dropping them (`mergeLiveMessages`).
7. Each composer remembers the agent, model and effort (`variant`) chosen **per session**, stored client-side (`localStorage` on web, SecureStore on mobile) and restored when the session is reopened; new sessions keep falling back to the last used model.

### 4.2 Permission approvals

1. The agent requests permission → `permission.asked` event with `Permission.Request` (`id`, `sessionID`, `action`, `resources`, `save?`, `metadata?`, `source?`).
2. The client shows a modal with the action and affected resources.
3. The user answers → `POST /api/oc/api/session/:id/permission/:requestID/reply` with `{ decision }` (`once` / `always` / `reject`). The session id resolves the request.
4. opencode emits `permission.replied` (`{ sessionID, requestID, reply }`) and all devices sync.
5. SSE does not replay across reconnects, so on (re)connect clients reconcile pending requests with `GET /api/oc/api/permission/request?location[directory]=<workspace>` for every workspace; otherwise a missed `permission.asked` would leave the agent blocked with no UI. Reconciliation is authoritative per directory: requests answered elsewhere are pruned, requests outside the queried directories are kept, and a directory that failed to answer never prunes anything.
6. Optional per-session **auto-accept** (a toggle next to the composer, stored client-side): incoming requests for that session are answered `once` automatically and the queue is drained on (re)connect. It is reversible — `once` never persists a rule in opencode. The setting is **inherited down the session tree**: a subagent child (`parentID`) answers automatically when any ancestor has it on, and Goal Mode's internal critic/judge sessions are **always forced** so a review never stalls on an approval card (`shouldAutoAccept` in `client-core`).

### 4.3 Authentication (single user, multiple devices, multiple servers)

- **Server profiles.** Every client keeps a registry of independent servers (`id`, `label`, canonical URL, auth mode, per-server device id, last used workspace/session). There is exactly **one active connection** at a time: one `Client`, one `QueryClient` and one SSE stream. Switching unmounts the previous authenticated tree (keyed by profile id), stops its stream and discards its cache, then restores the target profile's last workspace/session.
- **Web on the serving origin.** `POST /api/login` validates the password and sets a signed `HttpOnly`, `Secure`, `SameSite=Strict` cookie. The password never reaches client code. Profiles whose URL is the page origin always use this cookie and never store a token. The desktop app has no serving origin (it is served from `masterhand://app`), so every server is authenticated with a device token.
- **Remote servers from web, and every server from desktop.** A page cannot use another origin's cookie. Each profile authenticates separately with that server's password via `POST /api/devices`; the server returns its own signed device token, which the client stores per profile (`localStorage`, separate from the profile list) and sends as `Authorization: Bearer <token>`. Tokens are revocable (`DELETE /api/devices/:id`). No credential is ever reused across profiles.
- **Mobile (`apps/mobile`).** `POST /api/devices` validates the password and returns a Bearer token plus a device record. The app stores one token per profile in SecureStore and sends `Authorization: Bearer <token>` on every request. The stable install id (one per installation, its own key) is sent on every login so the same device is deduplicated and remains independently revocable.
- **Serving-origin scheme exception.** The profile whose URL is the page origin may be plain `http://` (LAN deployment with `COOKIE_SECURE=false`): its credential is the same-origin HttpOnly cookie and never leaves that origin. New remote profiles from web/desktop remain https-only; the native mobile client additionally accepts plain `http://` for private/link-local hosts (`allowPrivateNetwork`, ADR-47). A legacy mobile LAN URL is still accepted once during migration so the existing session is not dropped. Profiles are capped at 50 in both clients; mobile keeps the registry in one SecureStore JSON value (a split-storage refactor remains a documented follow-up if large lists approach the platform value limit).
- **CORS (bearer-only).** The BFF answers `Access-Control-Allow-Origin: *` with allowed headers `Authorization` and `Content-Type` on `/api/*`, including preflight, error responses (401/429/5xx), raw proxy/attachment responses and the SSE stream. It never sends `Access-Control-Allow-Credentials`, so a browser cannot replay a cookie cross-origin. `ALLOWED_ORIGINS` remains the **CSRF allowlist** for cookie mutations, not the CORS allowlist. `POST /api/devices` is exempt from the same-origin check because it is cookie-less, requires the password in the body and only returns a token.
- The BFF accepts either credential on protected routes. Both are signed with `SESSION_SECRET` and share the TTL configured by `SESSION_TTL_HOURS`.
- Device records live in SQLite (`GET /api/devices`, `DELETE /api/devices/:id`); multiple devices may be signed in at once for the same single user.
- Origin checks apply only to cookie-based mutations; Bearer requests are exempt (tokens are never attached automatically by browsers, so there is no CSRF risk).
- **Disconnect vs. remove.** Disconnect clears this device's session but keeps the profile. Remove forgets the profile. Both clear the local token and switch screens **before** any network call; the idempotent `DELETE /api/devices/:id` (or cookie logout) runs in the background, is never auto-retried, and reports a residual asynchronously. Revocation is skipped when another saved profile shares the same `deviceID` (same server under two hostnames), because deleting the device row would revoke both.
- **No redirects.** Every client-core request and the SSE fetch use `redirect: "error"`. A cross-origin redirect would otherwise be replayed as a same-origin request and attach the serving origin's cookie.

### 4.4 Notifications (in-app + local system notifications)

- The BFF's SSE relay drives in-app notifications in every client: `session.idle`, `session.execution.failed` (agent error) and `permission.asked` update a badge/indicator.
- Tapping a notification opens the corresponding session.
- Every client also shows local system notifications for the same four kinds: `session.execution.succeeded`/`session.idle` → "Agent finished", `session.execution.failed` → "Agent failed", `permission.asked` → "Permission needed", question `form.created` → "Question waiting". The foreground stays silent (banners/modals already cover it); events notify only when the client is not active, notifications are enabled (Settings > Notifications) and the OS permission is granted. Decisions are pure and shared (`packages/client-core/src/agent-activity.ts`): busy→idle required for finishes, user-interrupted turns never notify, critic/judge/fork sessions are ignored, permission/form ids dedup once. The device stores per-kind switches (`finished`, `failed`, `permission`, `question`) on top of the master switch; missing storage keeps every kind on.
- Web/desktop use the renderer's Web Notifications API (no preload/IPC surface in the Electron shell): the desktop app enables them by default because Electron grants the permission, while a browser asks once from Settings; a browser also requires HTTPS/localhost (Electron skips that gate for plain-HTTP LAN deployments). Alerts fire when the window is hidden, minimized or unfocused; clicking one focuses the window, switches workspace when needed and opens the session. Opening a session or starting a new turn closes its stale banners. Closing the desktop app stops alerts (no tray/background mode).
- Android uses `expo-notifications` (no FCM/APNs/Expo Push, no Play Console account) and keeps the master switch opt-in because the OS permission must be requested; enabling asks once and registers the background check. Tapping a system notification opens its session (same profile: switch workspace when needed; another saved profile: switch servers).
- Closed-app coverage is a periodic `expo-background-task` (WorkManager, minimum 15 min, Android decides the exact time): it reads the active profile + token from SecureStore, fetches `client.api.statuses()`, diffs against the persisted busy baseline (`masterhand.notifyBusy.<profileID>`) and notifies up to 5 finished sessions, then persists the new baseline (titles resolved best-effort via workspaces/sessions). The task only runs while the master switch and the `finished` kind are on (turning finishes off unregisters it); disabled, missing profile/token, or network/storage failures do nothing (best-effort, never throws, so the schedule survives). The foreground merges its workspace's busy sessions into the same baseline, so enabling starts fresh without back-buzz.
- Remote push (FCM/APNs) stays out of scope: no push tokens, no server-side fan-out, no store account. Instant delivery with the app killed is explicitly not guaranteed (15-minute floor + Doze); a foreground service would be the follow-up if instant matters.

### 4.5 Reconnection (mobile / background)

- SSE does not guarantee event replay.
- On reconnect (or when returning from background), clients refetch `GET /api/oc/api/session/:id/message` and replace their live state with the projection, except for the text/reasoning parts of a message still streaming (the projection does not carry them until the step closes).
- Streaming events are keyed: text/reasoning by `assistantMessageID` + `ordinal` (numbered per kind), tool parts by their call `id`. Deltas append; `*.ended` carries the final text; tool `success`/`failed` carries the result `content`.
- Client inactivity watchdog (60s without bytes → forced reconnect), reconnect when the tab/app becomes visible (`visibilitychange` on web; `AppState` on native, through the `forceReconnect` handle `useEventStream` returns) and when the network returns (`online`). A forced reconnect restarts the backoff ladder and cancels an already-scheduled retry, so returning to the foreground never waits out a grown delay.
- On (re)connect, `sessions`, `messages` and `statuses` are invalidated to reconcile missed events.
- The statuses poll merges its snapshot into the event-set cache (`mergeStatuses`): a status set by an event at/after the poll started wins over the snapshot, so a poll that raced `execution.started` cannot hide the Stop button; statuses missing from the snapshot with no fresh event are dropped as idle.
- Pending permissions are reconciled too (`GET /api/oc/api/permission/request` per workspace): a `permission.asked` lost while offline would otherwise leave the agent blocked with no prompt.
- Fallback without SSE: connection down → polling (messages every 5s, statuses every 4s); active turn → messages every 3s.
- Every client request has a deadline (configurable `timeoutMs`, default 30s; the BFF proxy bounds its upstream fetch at 60s with `504 opencode_timeout`), so a stalled socket rejects with a typed `RequestTimeoutError` instead of leaving a mutation latched in the UI. The composer shows "Sending…" while a prompt is in flight, keeps text typed meanwhile and, on timeout, warns and asks to check the chat before retrying: prompts are not idempotent, so there is no automatic retry. Before the deadline fires, the composer reconciles the send against the live history (`queryKeys.messages`): when the sent user message appears — the prompt was processed even if its response was lost — the send is confirmed, released immediately and the sent text cleared; the deadline with the warning only covers sends that cannot be confirmed.

### 4.6 Workspaces (isolated project folders)

- There is a single **workspaces root** (`WORKSPACES_ROOT`, default `<repo-root>/workspace`; `/workspace` in Docker), the folder opencode works in. Every **workspace** is a subfolder of it, tracked in the BFF (`workspaces` table in SQLite: `id`, `name`, `path`). Relative values are resolved against the repo root, so the path does not depend on the process `cwd`.
- Clients only send a **name**; the BFF sanitizes it to a single path segment (no separators, traversal or leading dots), derives `<root>/<name>` and creates the folder with `mkdir -p`. The name and the folder are the same, so arbitrary absolute paths can never be registered and everything stays isolated under the root.
- Clients pick a workspace; every opencode **location-scoped** call carries its `path` as `?location[directory]=`, session listing uses `?directory=` and session creation sends `location: { directory }` in the body. Sessions are therefore created in and listed for the selected folder.
- Every workspace is made its **own git root** (the BFF `git init`s it on creation and, for legacy folders, before the first session). opencode resolves its `project.directory` by walking up to the nearest `.git`/`.hg`, so a workspace nested inside the MasterHand repo would otherwise make opencode treat **MasterHand** as the project root: `/init` would edit `MasterHand/AGENTS.md`, the server's own `AGENTS.md` would be injected into the agent's context, and `/review` would diff the server. The workspace-level `.git` boundary also stops instruction discovery at the workspace.
- On session creation the BFF adds best-effort guardrails (never blocking creation): instruction entries `masterhand.workspace` (independent from `masterhand.preview`) rooting the agent in its exact directory — its project root and where `AGENTS.md` belongs — while allowing work outside it only when it is **100% necessary or the user explicitly asks**, and `masterhand.process`, which forbids broad process kills and points at the supported lifecycle; plus a session permission guard that allows external access (`external_directory: *`) so the agent can work in any project, denies `read`/`external_directory` on `/proc` and **reads/edits** of the engine data/config dirs so engine-side tools cannot reach or rewrite credentials (#219), and denies dangerous shell commands (`pkill*`, `killall*`, `fuser*`, `kill $(...)`, `npm run dev:stop*`, `docker compose down*`, `systemctl stop*`, …) so a broad kill cannot take down the agent engine. The v2 shell tool asserts the `shell` action (verified against 2.0.21); a numeric `kill <pid>` stays allowed. Shell access is not fully sandboxed (see §5): the Docker deployment runs agent shell commands as a separate unprivileged user (ADR-22), but an allowed command can still touch anything that user can reach.
- Deleting a workspace forgets it in MasterHand. With `?deleteFiles=1` (a checkbox in the UI) the BFF also removes the folder and its files; it refuses (`403`) when the stored path lies outside the root. Deleting a session calls `DELETE /api/session/:id` (the session id resolves its location) and removes its data.
- The BFF persists the list and owns folder creation/deletion; opencode works inside the same mounted root.
- **One BFF instance, one SQLite file.** The BFF is the single writer of `masterhand_data/masterhand.sqlite` (WAL, `synchronous = NORMAL`, `busy_timeout = 5000`; ADR-26). Running two replicas against the same volume is **unsupported**: each would own its own preview tunnels/PTYs and the SQLite file has a single-writer contract. Scale vertically, not with replicas.

### 4.7 Branch viewer (read-only)

Sessions of one workspace share its folder and its current git branch. The composer header shows that branch as a **read-only viewer**: icon + name, no button, no popover, no create/switch action. `GET /api/workspaces/:id/branches` reads it over git (`symbolic-ref` + `for-each-ref`); clients poll it every 5 seconds, so a branch the agent switches with its own shell tools (or a manual `git checkout`) appears without user action. The viewer hides itself when the workspace is not a git repository or the read fails. Branch mutations are the agent's job (or a terminal), never a MasterHand control.

### 4.8 Session previews (Cloudflare quick tunnels)

The agent usually runs a web project's dev server inside its own process/container, whose port the user's browser cannot reach. **Previews** expose it without publishing any port:

1. On first use, the BFF reserves a **fixed port** per session from `PREVIEW_PORT_RANGE` (persisted in the `preview_ports` table). Fixed ports survive BFF restarts and let a running dev server be re-exposed without restarting it. The allocator recycles the oldest mapping without a live tunnel when the pool is drained.
2. While previews are enabled, the BFF writes one session instruction entry (`PUT /api/experimental/session/:id/instructions/entries/masterhand.preview`, key `masterhand.preview`) telling the agent that the web server for the project listens on `0.0.0.0:<port>` (started by MasterHand's run control, §4.9) and how to accept the tunnel hostname; opencode includes instruction entries in the model's system context on every turn. No project files (`AGENTS.md`, `opencode.json`) are touched and the proxy forwards the body byte-for-byte on its allowlisted routes.
3. On an explicit **Start**, the BFF probes `PREVIEW_ORIGIN:<port>` over TCP and then spawns `cloudflared tunnel --no-autoupdate --url http://<origin>:<port> --http-host-header localhost:<port>` inside the BFF container, capturing the random `https://<name>.trycloudflare.com` URL from its output. The `Host` rewrite is what makes framework dev servers work through the tunnel: Vite's `server.allowedHosts` (and similar origin checks) reject the public hostname with `403`, while `localhost` is always allowed. The URL is served to clients, which embed it in an iframe (web/desktop) or a WebView (mobile). **Stop** kills the process; session deletion — including out-of-band `session.deleted` events — and BFF shutdown clean up too, and live PIDs are persisted so a restart after a hard crash reaps orphaned tunnels (only PIDs still confirmed to be `cloudflared`).
4. `PREVIEW_ORIGIN` is the host of the dev server as seen by the BFF: `opencode` on the Compose network, `127.0.0.1` in native dev. The quick tunnel makes an **outbound** connection to Cloudflare, so no inbound ports or DNS/certificates are needed.

**Restart hardening.** `stop()`/`stopAll()` bump a per-session epoch and kill a `cloudflared` that is still starting; the cancelled launch rejects with `preview_stopped` instead of publishing a tunnel, and the next Start always creates a fresh hostname. The manager retains `lastUrl` — the last announced URL — in memory across `stopped`, `starting` and `error`, while `url` remains non-null only while `running`; `forget()` and a BFF restart clear it. Clients cancel in-flight preview status queries before and after start/stop so a late GET cannot restore an older tunnel, and show the current URL (or the retained last one) with an Open action.

Quick tunnels are **public and ephemeral** (random URL per start, no authentication at the edge): an explicit testing feature, not a production hosting path. See the Risks table.

### 4.9 Managed dev server (run configuration)

Agents must not start or kill long-running servers: a broad kill (`pkill node`, `kill $(lsof -ti:PORT)`, `npm run dev:stop`) can take down the agent engine itself (§5). MasterHand owns the lifecycle instead:

1. A **run configuration** is stored per workspace (`workspace_runs` in SQLite: `command`, `args`, `cwd`, `source`, `updated_at`) and reused by every session of that workspace. The agent proposes it by writing `<workspace>/.masterhand/run.json`; the BFF validates the file and the user applies or edits it in the UI. The user can also edit it directly.
2. The command is **argv, no shell**: `command` is one executable and `args` a bounded list, so a shell string cannot smuggle a `pkill`. Shells and process-killers (`sh`, `bash`, `pkill`, `killall`, `xargs`, `docker`, `systemctl`, …) are rejected, arguments are bounded and `cwd` cannot escape the workspace. `{port}` is replaced with the session's reserved preview port (the same port the tunnel forwards) and `PORT` travels in the env.
3. On Start the BFF calls opencode's `POST /api/pty` in the session's directory with the title `masterhand:<sessionID>` and the validated argv; with `MANAGED_RUN_LAUNCHER` set (Compose) the PTY command is wrapped as `agent-exec --exec <command> <args>`, so the run drops to `agent` (point 5). On Stop it calls `DELETE /api/pty/:id`, which kills exactly that process tree. Concurrent starts coalesce per session (in-flight promise), so two devices cannot create two PTYs. After a BFF restart the state endpoint adopts a still-running PTY by its title instead of spawning a second server; deleting the session stops it, and clients poll `running` at a slow cadence so a dev server that dies on its own surfaces instead of showing a stale state.
4. Session creation writes the `masterhand.run` instruction: declare the command, never manage servers. The `masterhand.preview` instruction keeps the reserved port and the tunnel-host advice.
5. **Run isolation.** `MANAGED_RUN_LAUNCHER` (set to `/usr/local/bin/agent-exec` by Compose, empty in native development) wraps the PTY: `agent-exec --exec <command> <args>` execs the argv verbatim (no shell) after dropping to `agent` (uid 1001/gid 1000, supplementary groups cleared) and replacing the inherited environment with `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `LANG`, `TMPDIR` and a validated `PORT`. `OPENCODE_SERVER_PASSWORD`, provider keys, `NODE_OPTIONS`/`LD_*`, `GIT_*` and `SSH_AUTH_SOCK` never reach the dev server; the status still reports the user's command/args and `PORT` still carries the reserved preview port. `agent-exec` itself is rejected as a run command (it would turn the validated argv back into a shell). Native development leaves the variable unset, so runs inherit the user running `opencode serve` — Docker is the only isolation path.

### 4.10 Goal Mode (`/goal`)

A goal run wraps a session in an adversarial review loop: the main agent works the goal, an internal **critic** challenges the claimed completion (it may inspect the workspace and run commands/tests) and an impartial **judge** decides. The loop repeats until approval or the round cap; on cap the run pauses with the last verdict, awaiting a user decision (resume/cancel). All prompts are server-side constants; clients only render state and call the routes (`docs/bff/api.md` §Goal Mode).

1. **Protocol.** The BFF writes a `masterhand.goal` session instruction (completion-marker grammar) and prompts the main session. When the agent claims completion it ends its final message with `<masterhand:goal status="complete|blocked">{summary, evidence}</masterhand:goal>`; the critic answers `<masterhand:critique>{argument, issues}</masterhand:critique>` and the judge `<masterhand:verdict>{approved, reasoning, requiredChanges}</masterhand:verdict>`. Parsers are tolerant (last block wins, malformed JSON degrades to a phase retry) but strict enough to never treat prose as approval.
2. **Durable state machine** (`goal.ts`, tables `goal_runs`/`goal_settings`): `running → critiquing → judging`, plus `approved`, `paused` (cap or manual), `cancelled`, `error`. Each phase records the assistant-message baseline it prompts from, so event handling is idempotent. Critic and judge are child sessions (`parentID` = main session) writing their own instruction entries; the existing `rootSessions` filter keeps them hidden.
3. **Reliability rules** (ADR-32/33, `docs/past-mistakes.md`): non-idempotent calls (internal session create, prompts) reconcile a persisted marker before any replay; a failed turn re-drives its phase up to three times with incremental delays; a missing completion marker gets one corrective nudge and then errors; opencode's own provider retries only update the run note; a watchdog (and `server.connected`) reconciles lost idle events by checking `/api/session/active`; after a BFF restart in-flight runs become `paused` (never auto-resumed); cancel interrupts the awaited turn and removes the internal sessions.
4. **Transport.** Every transition is broadcast as a synthetic `goal.updated` frame through the existing SSE hub (`hub.emit`), carrying the same payload as `GET /api/sessions/:id/goal`, so no client polls. The clients keep a `useGoalRun` query seeded by that frame plus one refetch on reconnect (SSE has no replay).

### 4.11 Bounded retries and reconciliation (BFF ↔ opencode)

A single retry engine (`apps/server/src/retry.ts`, ADR-32) fronts every internal opencode call and the `/api/oc/*` proxy:

- **Idempotent operations** (`GET`/`HEAD`/`PUT`/`PATCH`/`DELETE`, plus the proxy's `agent`/`model` switches) retry transient failures — HTTP 408/425/429/5xx or a fast network error — with incremental backoff (×2, capped, ±25 % jitter) and a bounded attempt budget. Definitive 4xx answers pass through unchanged, and timeouts are not retried (multiplying a stall would hurt more than help).
- **Non-idempotent mutations** never replay blind. Internal session creation and every prompt carry a server-persisted marker (`masterhand.goal.role`, `masterhand.goal.delivery`; the clients' prompts carry `masterhand.delivery`): before a retry the engine asks opencode whether that exact marker exists (`GET /api/session/:id/message`, session list by `parentID`) and continues without replaying when it does. This makes a rate-limited prompt safe to retry and bounds the residual duplicate window (the marker check right after the failure).
- **Exhaustion is visible, never a hang.** The last upstream response (or transport error) reaches the caller; Goal Mode maps exhaustion to a resumable `error` state with the reason and the attempt count.

### 4.12 Board (kanban, one per workspace)

One board per workspace: columns with ordered cards (`title` + `description` now; future attributes land as typed columns + typed UI, never free-form JSON). The board follows the selected workspace — no extra selector beyond the existing workspace bar on both clients.

1. **Storage** (`store.ts`, tables `board_columns`/`board_cards`): `id` primary key, integer `position` per scope (`(workspace_id, position)` / `(column_id, position)` indexes), reindexed sequentially in a transaction on every affected mutation. No FK pragmas: column deletion removes its cards in the same transaction, and workspace deletion drops its board rows there too.
2. **Mutations are idempotent by design** (ADR-35, `docs/past-mistakes.md`): a card move is an absolute `(columnID, position)` assignment, creates carry a client-generated id (`INSERT … ON CONFLICT(id) DO NOTHING`, returning the current row), and deletes are idempotent — so a lost response is reconciled by a plain refetch/retry with no duplication and no marker lookup. One board per workspace is enforced at the trust boundary: a card move into another workspace's column (and a column id replayed under another workspace) answers `409 column_workspace_mismatch` and leaves the source board untouched; workspace resolution for frames is O(1) via `getBoardColumn`/`getBoardCard`, never a full-board scan.
3. **Transport.** Every successful mutation publishes a synthetic `board.updated` frame through the existing hub (`{ workspaceID, board }`, the same full-snapshot shape as `GET /api/board`), exactly like `goal.updated`: no client polls, other devices stay in sync, reconnect reconciliation refetches. Clients keep a `useBoard` query seeded by that frame (frame-beats-in-flight-snapshot guard like `useGoalRun`).
4. **Web drag & drop** (`@dnd-kit/core` + `sortable`): `DndContext` + per-column `SortableContext`; a drop commits the absolute position optimistically, then `PATCH`; on failure the board refetches and an error toast surfaces — no blind retry loop. Column reorder stays in menus (move left/right) in v1; columns do not drag.

## 5. Security model

| Layer | Measure |
|---|---|
| Network | Only the deployer's reverse-proxy port (and SSH) is public; BFF and opencode publish no ports, they live on the Compose internal network |
| Auth | Single password → signed cookie (web on the serving origin) or Bearer token (desktop, native, remote web profiles); login rate limit; CSRF origin check on cookie mutations |
| Secrets | `OPENCODE_SERVER_PASSWORD` and API keys only in the host `.env` / volumes; never in client code. Agent children get a cleared environment + allowlist, and engine credential stores/config/log are owner-only (see Process isolation) |
| Agent permissions | Per-session `permissions` PATCH injected by the BFF: external access allowed (`external_directory: *`), `shell` denied on broad-kill patterns (`pkill*`, `killall*`, `fuser*`, `kill $(...)`, `npm run dev:stop*`, `docker compose down*`, `systemctl stop*`, …), and `read`/`external_directory` denied on `/proc` plus `read`/`external_directory`/`edit` denied on the engine data/config dirs; `deny` is used because auto-accept bypasses `ask`. Optional deployer-side `opencode.json` remains available for broader policies |
| Workspace prompts | Every workspace is its own git root (so opencode's `project.directory` is the workspace, not the MasterHand repo); each session roots the agent in that directory with the `masterhand.workspace` instruction, allowing external paths only when strictly necessary or user-indicated |
| Process isolation | Agent shell commands **and managed dev servers** run as a dedicated unprivileged user (`agent`, uid 1001, primary group `node`) while `opencode serve` runs as `node` (uid 1000): a broad kill (`pkill node`, `killall`, …) gets `EPERM` and cannot signal the engine. The setuid helper (`deploy/agent-exec.c`) hardcodes the identity, removes supplementary groups, **clears the inherited environment** and exposes only `PATH`/`HOME`/`USER`/`LOGNAME`/`SHELL`/`TERM`/`LANG`/`TMPDIR` + a validated `PORT`; managed runs use its `--exec` mode (argv verbatim, no shell). Every new execution path must use this dropper — one that bypasses it runs as the engine uid. Engine-owned `opencode.db` (WAL/SHM inherit), `log/` and the config dir are `0600`/`0700` at every start, so the agent uid cannot read credentials or write engine state; `shell/` and `snapshot/` intentionally stay agent-accessible |
| Client proxy | `/api/oc/*` is a **method-exact allowlist** of the routes `client-core` uses (sessions/prompts/interrupts, permissions and forms, agent/model/provider/integration catalogs, provider/websearch credential connect/activate/delete, websearch). PTY/terminal/shell, fs, config, plugin, mcp, session create/list/get/patch, `/api/info`, `/api/event`, `/api/command`, `prompt_async` and `GET /api/credential` answer `404 not_found` before any upstream call; encoded slashes are refused. The BFF's own `callOpencode` paths are unaffected |
| System | Unprivileged containers; opencode isolated from the public network; host firewall recommended |
| Engine-side residual | #219 covers engine read tools with session `read`/`external_directory` denies on `/proc` and the credential store (lexical match: symlink escapes stay a documented residual); #218 disables project-level plugin/config discovery (`OPENCODE_CONFIG_PROJECT_DISABLE=true`), so workspaces can no longer execute code as `node` (uid 1000) |
| Future | TOTP, stricter agent container/sandbox (network and resource limits) |

> Note: an agent with shell access on the host is RCE by design. The mitigation is not to remove the feature but to limit the blast radius (unprivileged containers, `deny` guards on the commands that can kill the stack, minimal surface; a stricter agent sandbox is in the backlog).

**Denied-command audit.** Every command blocked by the session permission guard is kept for diagnosis: the BFF correlates opencode's `session.tool.called` event (which carries the command) with the matching `session.tool.failed` carrying `error.type = "permission.rejected"`, stores an `audit_events` row (session, command, reason, timestamp) and exposes it through `GET /api/audit`. Web (`AuditPanel`) and mobile (`AuditModal`) show the log with a clear action, so an incident like "the model tried to stop the server and something died" can be traced to the exact command and the reason it was blocked.

## 6. Deployment (Docker Compose)

The stack deploys with a single command (`docker compose up -d`) on any host with Docker. **TLS is the deployer's responsibility** and can be provided by any reverse proxy or tunnel; the repository does not ship a proxy configuration.

```
deploy/
├── docker-compose.yml     # masterhand (BFF) + opencode, BFF port published
├── docker-compose.dev.yml # dev override: same stack, hot-reloading BFF/web
├── server.Dockerfile       # BFF + web build (multi-stage; `dev` target for hot reload)
├── opencode.Dockerfile     # pinned opencode + agent-exec sandbox
├── .env.example            # OPENCODE_SERVER_PASSWORD, MASTERHAND_PASSWORD, SESSION_SECRET, ...
└── .env.dev.example        # same variables, development values
```

| Service | Image | Ports | Volumes |
|---|---|---|---|
| `masterhand` | build of `apps/server` (also serves the static web build) | `${MASTERHAND_BIND:-0.0.0.0}:${MASTERHAND_PORT:-8787}` → `8787` | `masterhand_data` (SQLite) |
| `opencode` | `opencode.Dockerfile` (pinned version) | none (internal `4096`) | `opencode_config`, `opencode_data`, `./workspace` (shared with the BFF, which creates each workspace folder) |

- `restart: unless-stopped` on all services → the host restarts and the stack comes back on its own.
- The deployer points their own TLS/domain at the published BFF port and sets `ALLOWED_ORIGINS` if a different origin proxies to it. Bind to `127.0.0.1` with `MASTERHAND_BIND` when the reverse proxy runs on the host.
- Provider authentication: `docker compose run --rm opencode auth login` (persists in the `opencode_data` volume; 2.0.6 keeps credentials in `opencode.db`, not `auth.json`).
- Agents work under `./workspace` (bind mount) so files can be inspected/versioned from the host; the BFF creates one subfolder per workspace there. Agent shell commands and managed dev servers run as `agent` (uid 1001, group `node`) via the setuid `agent-exec` dropper (`-c` for shells, `--exec` for the run PTY; `MANAGED_RUN_LAUNCHER` points at it), which also clears the inherited environment; both services run with `umask 002` and the mount must be group-writable by gid 1000 (see the deployment runbook). Engine-owned `opencode.db`, `log/` and the config dir are owner-only at every start, so the agent uid cannot read credentials or write engine state.
- Backups: volumes `masterhand_data`, `opencode_data` and `opencode_config`.
- Session previews: the `masterhand` image bundles `cloudflared`; Compose sets `PREVIEW_ORIGIN=opencode`, so the tunnel targets the dev server inside the opencode container. The BFF needs **outbound Internet** and the agent must bind the reserved port to `0.0.0.0`. Set `PREVIEW_ENABLED=false` to disable the feature.
- Upgrade: opencode is pinned (`OPENCODE_VERSION`, v2); `docker compose build && docker compose up -d`. **Back up the `opencode_data` volume before the first v2 start**: v2 migrates v1 session data on boot and the beta warns data may be reset. Track the migration with `GET /api/experimental/migration/v1`.
- See `docs/runbooks/deployment.md` for concrete TLS options.

### 6.1 Development on the same stack

Development does not diverge from the deployment: it layers
`deploy/docker-compose.dev.yml` on top of `docker-compose.yml`, so both share the
**same services, images, internal network (`opencode:4096`), paths (`/data`,
`/workspace`) and environment contract**. The override
only changes how the BFF/web run: `deploy/server.Dockerfile` gains a `dev` target
(dev dependencies from the same `base` stage) and the sources are bind-mounted so
`tsx watch` and Vite reload in place, running as the same `node` user
(uid 1000, `umask 002`) as production; `opencode` is left untouched, which keeps
the `agent-exec` sandbox (ADR-22) and the preview tooling identical to
production. `deploy/.env.dev` uses the same variable names as `.env.example`, and
`npm run dev` wraps the whole command. Desktop and mobile still run on the host
(GUI/device) against the containerized BFF; the fully native `scripts/dev.mjs`
flow stays as a fallback (`dev:native:*`). See `docs/runbooks/development.md`.

| ADR-46 | **Android release APKs keep the constructors R8 strips from reflective classes, and the release workflow gates the built dex.** SDK 58 builds release with R8 full mode; WorkManager (via `expo-background-task`) creates `WorkDatabase_Impl` and its input mergers by reflection, so Room's class-only keep rule is not enough. `apps/mobile/app.json` passes `-keep class * extends androidx.room.RoomDatabase { <init>(); }` and `-keep class * extends androidx.work.InputMerger { <init>(); }` through `expo-build-properties.extraProguardRules`, `expo-background-task`/`expo-task-manager` stay on the SDK-58 patches that match WorkManager 2.10.5, the GitHub asset is named `MasterHand-<version>.apk`, and `scripts/check-android-dex.mjs` dumps `classes*.dex` with `dexdump` and fails the job before upload when a constructor is missing. F-Droid still stores its standard `dev.togudv.masterhand_<versionCode>.apk` filename | v0.2.0 shipped `app-release.apk` with `WorkDatabase_Impl.<init>` stripped: the app crashed in `androidx.startup.InitializationProvider` before `MainActivity` and before React Native, and the signature check still passed. The guard turns this class of regression into a failed release instead of a bad download; the upstream `expo-background-task` 58.0.12 bump alone is insufficient because it only fixes the `InputMerger` rule | Disabling minify for release (larger APK, loses R8 optimization), trusting the dependency bump alone (WorkManager 2.10.5 keeps `InputMerger`, not Room's generated database), a manual device smoke test only (easy to skip and not tied to the artifact), leaving the Gradle `app-release.apk` name (users cannot tell which app/version they downloaded) |
| ADR-47 | **Plain-http LAN access is a native-mobile-only, opt-in scope, and `/api/health` identifies the server for discovery.** `normalizeServerUrl` accepts `http://` only for RFC 1918 / link-local / ULA IPv4+IPv6 addresses and `.local` / `.home.arpa` names, and only when the caller passes `allowPrivateNetwork`; scheme-less private input is assumed `http://`. Only the mobile entry points pass the option (`App.tsx`, `ServersScreen.tsx`). Web/desktop never pass it: the web build keeps https for remote servers (the exact page origin remains its only bypass) and the bundled desktop keeps its pre-existing no-cookie-origin exception (ADR-45). Public origins still require https everywhere. `apps/mobile/app.json` enables Android cleartext through `expo-build-properties` and declares iOS `NSLocalNetworkUsageDescription` plus `NSAppTransportSecurity.NSAllowsLocalNetworking`; the Android release job runs `scripts/check-android-manifest.mjs` after the dex gate, so an APK whose merged manifest lacks `usesCleartextTraffic=true` never ships. `GET /api/health` now carries `app`/`version` so a LAN probe can discard other services answering on the same host and port; the fields are trivially spoofable and are explicitly not authentication | A phone on the same LAN cannot present a publicly trusted certificate for a private address, so https-only made the native client unusable at home without external infrastructure. The scoped option keeps the public-origin rule intact while accepting the realistic threat model: WPA2/3 protects against devices that do not know the Wi-Fi password, but a peer that knows the PSK and captured the handshake can derive the per-client key and decrypt unicast, and an active LAN attacker (rogue AP, ARP spoofing, hostile peer) can read or modify the traffic; the credential at stake is a device token that can drive opencode's tools on the host — more than a token read. Accepted for a trusted home LAN and recorded as a product decision; `app`/`version` only filter discovery noise and never grant access | Public CA (impossible for a private IP), user-installed CA (manual trust step on every device), tunnel/VPN (extra infrastructure, domain or account), mDNS/multicast discovery now (native module, multicast commonly blocked on Android; deferred as P3, not shipped), a global `allowInsecure` for mobile (would also accept public http; the scoped option does not) |


## 8. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Poorly secured public exposure | Critical (RCE) | BFF with auth, rate limit, opencode on the internal network only, `ask` permissions, unprivileged containers |
| Public preview tunnel | High (data exposure) | Quick tunnels are opt-in per session and explicitly for testing; the random URL is unknown until started, and `PREVIEW_ENABLED=false` disables the feature server-wide. Previews are never for production data |
| SSE drops on mobile/background | High (stale UI) | Refetch + dedupe by `part.id`, fallback polling |
| Missing native push reduces awareness | Medium | In-app notifications plus Android local notifications (foreground SSE observer + 15-minute background check); remote push stays out of scope |
| SSE streaming from React Native | Medium | Mobile uses `expo/fetch` (streaming-capable) as the fetch implementation; polling is the fallback |
| Incompatible changes in opencode's API | Medium | Pinned version + regenerated SDK types |
| Uncontrolled model cost | Medium | Visibility of active sessions; abort sessions from any client (`/session/:id/abort`) |
