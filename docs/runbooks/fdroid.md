# Runbook — Self-hosted F-Droid repo and Android updates

MasterHand ships Android builds through a self-hosted F-Droid repository (#133): every `v*` tag builds a signed release APK, attaches it to the GitHub release, and refreshes the repo on the `fdroid` branch. The Android app shows a "New version available — Open F-Droid" banner (BFF manifest first, F-Droid index as fallback) and a Settings > About section.

The stable repo URL (added in F-Droid → Settings → Repositories) is:

**`https://togudv.github.io/masterhand/fdroid/repo/`**

The human landing page is `https://togudv.github.io/masterhand/` (the Pages root, where `index.html` lives).

## 1. One-time setup (maintainer)

### 1.1 Create the signing key (once, forever)

The same key signs every APK **and** the repo index. Android treats a key change as a new app identity (users must uninstall/reinstall), so this key must never change and must never be committed.

```bash
keytool -genkeypair -alias masterhand -keyalg RSA -keysize 4096 -validity 10950 \
  -storetype PKCS12 -keystore masterhand-release.keystore
```

PKCS12 uses **one password for the store and the key** (Java ignores a separate `-keypass`). Set `ANDROID_KEYSTORE_PASSWORD` and `ANDROID_KEY_PASSWORD` to that same value.

Back the keystore up offline (password manager + an offline copy). Losing it means a new package identity and a "conflicting signature" upgrade wall for every user. Key custody is documented here and nowhere else: whoever holds `masterhand-release.keystore` plus its password owns the Android release identity.

### 1.2 Add the Actions secrets

| Secret | Content |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 masterhand-release.keystore` |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore password |
| `ANDROID_KEY_ALIAS` | `masterhand` (or your alias) |
| `ANDROID_KEY_PASSWORD` | Key password (same as the keystore password for PKCS12) |

The workflows decode the keystore into the runner's workspace, use it to sign the APK and the F-Droid index, and delete it before committing — it never reaches the repository, the APK, or the logs (all four values are masked).

### 1.3 Enable GitHub Pages for the repo

The `fdroid` branch is created automatically by the first release (the script falls back to `git checkout --orphan fdroid`). After that first run:

1. Repository Settings → Pages → Build and deployment → Deploy from a branch.
2. Branch: `fdroid`, folder: `/ (root)`.
3. The repo lives under `fdroid/repo/` in that branch, so the index is served at `…/masterhand/fdroid/repo/index-v2.json`.

Branch layout (the branch root is the Pages site):

| Path | Committed? | Purpose |
|---|---|---|
| `index.html` | Yes | Human landing page with the repo URL and a release download link |
| `.nojekyll` | Yes | Serve the repo files verbatim from Pages |
| `fdroid/config.yml` | Yes (no secrets) | `repo_url`, `repo_name`, `repo_icon`, `repo_keyalias`, `keystore` |
| `fdroid/repo/*.apk` | Yes (old APKs kept) | One `<package>_<versionCode>.apk` per release |
| `fdroid/repo/index-v2.json`, `index-v1.jar` | Yes | Generated by `fdroid update -c`, signed with the release key |
| `fdroid/metadata/dev.togudv.masterhand.yml` | Yes | F-Droid listing metadata |
| `fdroid/icon.png` | Yes | Repo icon (the desktop brand mark) |
| `fdroid/repo.keystore` | **Never** | Decoded per run, deleted before commit |

The committed `config.yml` never carries passwords. The script appends `keystorepass`/`keypass` to a throwaway copy (`config.yml.keep` restores the clean file before the commit).

## 2. Cutting a release (server + Android + desktop together)

```bash
# 1. Bump every version reference (package.json files + app.json version and
#    versionCode), sync the lockfile, commit and tag. Final vX.Y.Z only:
#    prereleases notify stable users as if they were final (the semver compare
#    strips suffixes).
node scripts/release.mjs 0.2.0

# 2. Push main and the tag (this triggers the release workflow).
git push origin main v0.2.0
```

The workflow (`release`, jobs `preflight` → `image` / `android` / `desktop` →
`publish`):

1. `preflight` derives the version from the tag and fails fast when any
   `package.json`, `apps/mobile/app.json` (`expo.version`) or
   `android.versionCode` differs (see `scripts/check-release-versions.mjs`).
2. `image` derives the identity from the tag (`0.2.0` + commit SHA), builds/pushes
   `ghcr.io/togudv/masterhand:0.2.0` + `:latest`, the opt-in updater image
   (`masterhand-updater`), and generates `version.json`.
3. `android` `expo prebuild` + `./gradlew assembleRelease`, signed with the
   secrets keystore, and verifies the APK certificate against the keystore.
4. `desktop` builds the Linux AppImage, the Windows NSIS installer and the
   macOS universal DMG/ZIP, with the `latest*.yml` auto-update channel files.
5. `publish` creates `v0.2.0` with `version.json`, the APK and the desktop
   assets, then runs `scripts/fdroid-repo.sh`: copies the APK, runs
   `fdroid update -c`, signs the index, and pushes the `fdroid` branch (a no-op
   when nothing changed).

### 2.1 Repair a failed F-Droid run (without moving the release tag)

The release is already published when `publish` reaches F-Droid, so never move
the tag to fix the repo. Use the manual workflow — it downloads the APK from the
existing release and runs the same script:

```bash
gh workflow run fdroid.yml -R ToguDV/masterhand -f tag=v0.1.0
gh run watch -R ToguDV/masterhand
```

## 3. `versionCode` contract

`android.versionCode` is derived as `major*10000 + minor*100 + patch` (`0.1.0` → `100`; helper `androidVersionCode()` in `client-core`, unit-tested) and **never decreases**: F-Droid and Android both refuse "upgrades" to a lower code. Old APKs stay in `fdroid/repo/` so existing installs keep a valid index. Forks: the GHCR image path in `release.yml` is the owner's (`ghcr.io/togudv/masterhand`); point it at your own registry when forking.

## 4. Client behavior

- The banner compares the **installed** build (`expo-application`: `nativeApplicationVersion`/`nativeBuildVersion`) against the BFF's `GET /api/update` first; when the BFF is unreachable or predates the route it fetches `index-v2.json` from `.../fdroid/repo/` and compares `versionCode` (then semver on ties). Every failure is "no notice", never an error.
- The only action is **Open F-Droid**: a `market://details?id=dev.togudv.masterhand` intent (handled by `org.fdroid.fdroid`), falling back to the landing page `.../masterhand/`. Explicit non-goals: no `REQUEST_INSTALL_PACKAGES`, no APK-installer intent, no `expo-updates` — the user installs through F-Droid, where signatures are verified.
- Settings > About shows the installed version/build, the latest known release, the last check, and the same F-Droid entry points.

## 5. Privacy

Like the server update check, no device contacts GitHub for the happy path: the BFF already fetched `version.json`. The F-Droid index fetch happens only when the BFF check yields nothing (offline server, old BFF), and it goes to the self-hosted repo URL — never to F-Droid.org or the Play Store.

## 6. Troubleshooting

- **Workflow fails at the version guard:** `app.json` still carries the old version. Bump it (+ `versionCode`), amend, retag (`git tag -d` + `git push origin :vX` for an unreleased tag only — never move a published tag).
- **`fdroid update` says `repo_url needs to end with /repo`:** the repo layout is the standard one; `config.yml` must use `https://togudv.github.io/masterhand/fdroid/repo` (no trailing slash). The client adds the same URL with a trailing slash.
- **`fdroid update` says `repo_keyalias`/`keystorepass` not found:** the current `fdroidserver` reads `config.yml`, not the old `config.py`. The script writes `repo_keyalias`, `keystore`, `keystorepass` and `keypass`; the committed file only keeps the non-secret keys.
- **`apksigner not found`:** the `publish` and `fdroid.yml` jobs install the Android build-tools with `android-actions/setup-android@v4`; a local run needs the SDK build-tools on `PATH`/`ANDROID_HOME`.
- **`fdroid update` signs with the wrong key:** the branch's `config.yml` must keep `keystore = "repo.keystore"` and the release alias; the script overwrites both every run. If a foreign index was ever pushed, clients pin the first key they saw — re-adding the repo may be required.
- **Banner never appears:** check `GET /api/update` on the BFF (server log + `UPDATE_MANIFEST_URL`), then the index (`curl …/fdroid/repo/index-v2.json`). The banner needs a strictly newer `versionCode`/version than the installed build.
