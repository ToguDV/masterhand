# Past mistakes — reliability edge cases to keep in mind

**Read this before adding or changing any operation that mutates server state** (sending a prompt, creating/deleting a session or workspace, answering a permission/form, starting/stopping the run or preview, finishing an isolated session, revoking a device, …).

PRs [#62](https://github.com/ToguDV/masterhand/pull/62) and [#63](https://github.com/ToguDV/masterhand/pull/63) fixed one family of failures in the web composer. The same root causes can reappear anywhere a client talks to the BFF/opencode over an unreliable transport. This document records them — and the rules they produced — so new code does not reintroduce them or repeat a class of mistake we already paid for.

**Every resolved issue must leave its failure class here** (see `WORKFLOW.md` §"Working from an issue"): a new/updated rule, checklist item or established pattern. A fix without that trace is not done.

## The failure family

| # | Root cause | Typical symptom |
|---|---|---|
| A | **Unbounded async operation** with no deadline | A `busy`/`sending` flag latches forever; the UI looks stuck until reload |
| B | **Optimistic state clobbering** during a slow operation | Text typed while sending is wiped when the (late) response arrives |
| C | **Lost/ambiguous response** on a non-idempotent mutation, with no second channel | False "could not …" after the server actually applied it; blind retry duplicates work |
| D | **Race between a timeout fallback and a late confirmation** | A confirmed success still surfaces a failure/warning |
| E | **Partial failure leaves a resource orphaned** | A forked session, spawned process or created record that no one tracks/removes |
| F | **Destructive cleanup acting on an unverified store** | Startup/background maintenance deletes valid records or uncommitted work while a volume was missing, stale or partially mounted |

## Rules

1. **Every request has a deadline.** All BFF/opencode calls go through `client-core`'s `request`/`authedFetch`, which apply `ClientOptions.timeoutMs` (default 30 s) and raise `RequestTimeoutError`. On the server, every internal opencode call is bounded too (`OPENCODE_TIMEOUT_MS`, default 10 s, normalized to `OpencodeTimeoutError` and answered `504 opencode_timeout`) and the public proxy keeps a 60 s budget: no BFF route may await an upstream promise forever. Never call `fetch` directly for server state, and never await a promise whose rejection can leave a flag set. `timeoutMs: 0` only for deliberately unbounded streams.
2. **A deadline that is too short for a legitimate operation is a bug.** Long operations (`finish` = commit + push + PR; run/preview readiness) need their own budget or a documented override, not the generic 30 s. Note the BFF proxy bounds upstream calls at 60 s; treat the client deadline as intentionally shorter for interactive calls.
3. **Only clear/overwrite local state that is still what you sent.** Compare against the value captured at submit time (web composer uses `textRef`); never blow away edits the user made while the request was in flight.
4. **Distinguish "timed out / unknown" from "failed".** A `RequestTimeoutError` means the operation **may have succeeded**. Show an ambiguity message, never a hard failure, and never auto-retry a non-idempotent mutation (prompts, create session, answer form/permission, start run/preview, PR creation). **One exception** (ADR-32, 2026-10-09): a retry is allowed when the outcome is *proven* through a server-persisted marker first — the goal orchestrator and the proxy's delivery-marked prompts replay only after the marker lookup shows the mutation did not land, and the retry carries bounded attempts with incremental backoff. Blind replay is still forbidden everywhere.
5. **If a second channel can confirm the mutation, use it.** opencode events (`permission.replied`, `form.replied`, `session.*`) and the live history are reconciliation sources. On confirmation, treat the operation as success and suppress the pending error/warning. A late confirmation must beat an earlier timeout rejection.
6. **Bound and clean up partial failures.** Register created resources (fork id, PTY, record) as soon as they are known — before the follow-up request — so both the failure path and unmount cleanup can remove them. Do not leak a fork/spawn if the second step fails.
7. **Guard against double submit synchronously.** A React state flag is not a lock: two events in the same tick can both read it as `false`. Use a ref for in-flight guards on non-idempotent actions.
8. **Reconcile stale state.** When an entity is deleted/renamed elsewhere (`session.deleted`, workspace list change), clear references to it (open session, cached panels) instead of leaving a mounted view pointed at a 404.
9. **Bound polling of transitional states.** `starting`/`retry` polls need a cap/backoff and a timeout state; an unbounded 1.5 s refetch spins forever when the transition never completes.
10. **Correlate mutations with a server-persisted marker, not text + time.** Matching by text + time is fragile: identical consecutive sends, another device sending the same text, or server-side text normalization produce false positives (and false negatives). Prefer a correlation the server stores and returns verbatim — the prompt body accepts `metadata` and opencode persists it on the created user message, so MasterHand sends a per-send marker there (`delivery.ts`) and confirms only on it. When no marker channel exists, document the accepted residual risk with tests.
11. **Destructive cleanup only on a demonstrably healthy store.** Before deleting (or even moving) worktree records or folders, confirm the volume is real: the sentinel written by a previous successful pass, or live evidence that recorded paths still exist. When it cannot be confirmed — late/failed mount, DB restored from an older backup — skip the pass and log why. Prefer quarantine (rename, keep the branch) over delete, so uncommitted work stays recoverable, and never drop a record on a single `existsSync` observation alone.
12. **Serialize non-idempotent check→create on the server.** A client-side guard cannot stop two devices (or a retry racing the first request) from both passing a status check and creating two resources. Coalesce per entity with an in-flight promise (the architecture assumes a single BFF instance; see §4.6) and make stop/cleanup wait for it.
13. **Cap and observe the resources you share.** Unbounded container logs and memory are a full-disk/OOM incident waiting to happen when SQLite and the workspaces live on the same host: cap them (`LOG_MAX_SIZE`, `deploy.resources.limits`) and surface exhaustion (`/api/status.storage.low`) so the user acts before storage fails.
14. **Infrastructure failures degrade, never cascade.** Advisory writes (`touch`, audit) are best-effort and logged once; storage failures map to a typed `503 storage_unavailable` plus a status flag instead of opaque 500s; an expected constraint race maps to `409`/a retry; and a corrupt database fails loudly at boot with a restore pointer rather than serving broken requests. **Route-level catch-alls rethrow storage failures (`isStorageError`) before their typed fallbacks and before any rollback/cleanup** (`goalFailure`, `schedulerFailure`, the isolated-create catch, the run/preview catches): a `SQLITE_FULL` while persisting a record is infrastructure, not a domain failure, and destroying a healthy worktree or answering `500` hides the actionable cause from the client banner.
15. **Never block the event loop with synchronous process or filesystem work.** `spawnSync`/`execSync`/`mkdirSync`/`rmSync` on request paths freeze the whole single-process BFF: SSE pings stop, clients lose events and every request queues behind a 60 s child deadline. Use async `spawn`/`fs/promises` behind an injectable runner for tests; a timed-out child is killed **as a process group** (SIGKILL to `-pid`) so hooks/credential helpers cannot keep its pipes open past the deadline. Request-path filesystem reads go the same way (#200): `/api/status` serves `statfs` from a ~15 s TTL cache (the sync injection point stays for cheap test doubles), the run file reads through `fs/promises`, the tunnel PID file is a serialized async RMW chain (a track racing an untrack cannot lose an update), `/proc/<pid>/comm` reads are async, and `index.html` is read once at boot instead of per SPA navigation. Advisory PID writes stay best-effort and state still flips synchronously — only the file write waits (`stop`/`stopAll`/reap are async for that reason).

### Security boundary rules (2026-10-20 audit, C18)

The model: a workspace is agent-writable and **untrusted**; the BFF holds `/data` and its secrets; opencode and the agent run as different users. Every one of these rules exists because the audit found the boundary crossed.

16. **Never hand a child process the BFF environment when that child can execute repository-controlled content.** Git children get an allowlist (`PATH`, a private empty `HOME`, `GIT_TERMINAL_PROMPT`, explicit `GIT_*` only), command-scope `GIT_CONFIG_*` neutralization (`core.hooksPath=/dev/null`, `core.fsmonitor=false`, `credential.helper=`, `core.sshCommand=`, `commit.gpgSign=false`), `--no-verify` on commit/push, and a preflight that rejects repo-local config able to execute code (filters, diff/merge drivers, includes, credential helpers, `gpg.program`, submodule update commands, URL rewrites). `safe.directory` is scoped to the exact repository path being operated on — never `*`, and the image-level `/workspace` entry does not cover `/workspace/<name>`. A deny-list is defense in depth, not a proof: a concurrent writer can still race the preflight (TOCTOU).
17. **Bound request bodies before parsing them.** Unauthenticated and proxy routes need a hard body cap (Hono `bodyLimit`: 64 KiB for login/devices, `PROXY_BODY_LIMIT_MB` for `/api/oc/*`), counting chunked bodies too; reject `413` before buffering, and cap password length before hashing. A missing cap is an OOM waiting for one chunked request.
18. **Rate-limit failures, never successes.** Check the credential **first**, count only wrong attempts per socket IP, let the correct password through even when the budget is spent, and evict expired keys (TTL + LRU). Counting successes lets anyone who can reach the port lock the owner out; an unbounded map is a memory leak under IPv6 rotation.
19. **Secrets at rest are owner-only; weak configuration fails loudly.** Create the data dir `0700` and the DB/WAL/SHM/backups/PID files `0600` from creation (not after the first write), set the backup CLI umask, require production secrets of at least 32 bytes and reject example/placeholder values at boot, and parse booleans strictly (`COOKIE_SECURE=True` must not silently mean false; an unknown value must abort).
20. **Outbound requests driven by caller input need a target guard.** Keep private LAN ranges allowed when that is a documented feature (ADR-30), but refuse loopback, unspecified, link-local/cloud-metadata, multicast and reserved targets — including hostnames that resolve to them (check every resolved address) and IPv4-mapped IPv6. Reuse the existing timeout budget. Residual risk: DNS rebinding between lookup and connect, and redirects (document it).
21. **Validate every path and ref before it becomes argv or a log line.** `decodeURIComponent` on a path can throw `URIError` (answer `400 invalid_path`, never a 500 stack); branch/base-ref values accepted from a repo or client must pass `isValidBranchName` before reaching `git` (a `--force` name is an option, not a ref); scheduler names/prompts and other persisted text need the same caps as goals/board fields (`invalid_*`, 400).
22. **A privilege drop is not an environment boundary.** A different uid keeps signals out but forwards everything else: clear the inherited environment and install an allowlist (the `agent-exec` helper forwards only `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `LANG`, `TMPDIR` and a validated `PORT`), or `OPENCODE_SERVER_PASSWORD`, provider keys and `NODE_OPTIONS`/`LD_*` reach repository code. **Every execution path must use the same dropper** — shell commands and managed-run PTYs both go through `agent-exec`; a new PTY/spawn path that bypasses it defaults to the engine uid (the #179 failure). Engine-owned secret stores, config and logs are owner-only at every start (`opencode.db` and its WAL/SHM `0600`, `log/` and the config dir `0700`, `auth.json` `0600` when present and fail-closed, the BFF's provider config `0600`), so the `agent` uid can neither read nor write engine credentials; `shell/` and `snapshot/` stay agent-accessible by design. Runtime evidence (2026-10-20, opencode 2.0.6 dev stack): a managed run reported uid 1001/gid 1000 with no supplementary groups, exactly the allowlisted env (`PORT=3222`, no `OPENCODE_SERVER_PASSWORD`), `kill -0 1` failed, the DB/config/log were unreadable and the workspace writable; `POST /api/oc/api/pty` answered `404` while `GET /api/oc/api/model` answered `200`; `deploy/agent-exec-drill.sh` passed. Residual, tracked separately: [#216](https://github.com/ToguDV/masterhand/issues/216) (`GET /api/credential` is unavailable in 2.0.6 while clients call it; the E2E mock implements it), [#217](https://github.com/ToguDV/masterhand/issues/217) (`/api/provider` and `/api/model` include `settings.apiKey`; verify/redact), [#218](https://github.com/ToguDV/masterhand/issues/218) (project-level opencode plugins/config may execute as the engine) and [#219](https://github.com/ToguDV/masterhand/issues/219) (engine read tools can reach `/proc` and the credential store).

### Persistence rules (#186)

23. **Schema changes ship as immutable, ordered migrations.** Never edit production tables at boot with `CREATE TABLE IF NOT EXISTS` or an out-of-band `ALTER TABLE`: `IF NOT EXISTS` cannot add a column to an existing table, and the prepared statements created right after the DDL make the missing column a hard boot failure for every existing installation. Append a `{ version, description, statements }` entry to `apps/server/src/migrations.ts` (v1 is the frozen baseline), run its statements and `PRAGMA user_version = version` in one transaction so a failure rolls back to the previous version, never replay an applied version on reopen, and refuse to boot a database whose `user_version` is newer than the build (an older binary cannot understand a newer schema). Every migration failure keeps the restore pointer (`docs/runbooks/backups.md`); a shipped migration is never edited.

### Identity rules (#193)

24. **Never derive identity from mutable display data.** A device row keyed by `name` merged every phone that shipped the same default label: revoking the lost one also revoked the other, and `lastUsedAt` could not tell them apart. Identity must be a stable value the client owns and persists (the device `installID`, generated once per installation under its own storage key), with a unique constraint on it and an idempotent conflict path (re-read the winner). Names stay editable labels; "same label" must never mean "same entity", and changing the label on re-login must not change or duplicate the row. Clients without the stable id keep the documented fallback (a new row per login), never a best-effort match on mutable fields. Sign-out revokes (deletes) the device row but keeps the install id, so the next sign-in registers a fresh row with the same stable identity — it reuses the id, not the row.

### Isolated-create reconciliation rules (#185)

25. **A deadline on a non-idempotent create is not proof of failure — reconcile the persisted marker before rolling the resource back.** `POST /workspaces/:id/sessions` created a worktree, timed out waiting for opencode's create response and immediately removed the worktree; when the create had actually landed, the session was stranded in a directory MasterHand had already deleted and could never be listed, so the client's "may have applied" reconciliation had nothing to find. A timeout must leave the just-created resource alone: look the client's persisted marker up **fresh** (bypass the aggregation cache, scoped to the directory MasterHand just created), adopt the session with the same isolation record the success path writes and answer `201`, or answer `504` and leave the worktree to quarantine/reconcile (rule 11) when the marker cannot prove the create landed. If the workspace row disappeared while that deadline ran, quarantine the unconfirmed worktree immediately (`worktrees.quarantine`: rename, branch kept) instead of leaving it to a boot pass that only walks existing workspaces; if the directory is already gone, only log it. Never delete a session that is merely unconfirmed, and keep destructive rollback for **demonstrated** failures (a definitive non-ok/error response). This is rule 4 applied to resource cleanup: "unknown" is not "failed".

### Finish/PR reconciliation rules (#187)

26. **Coalesce a provider check→create per entity, reconcile against the provider, and never persist a fallback as the real result.** `POST /isolated-sessions/:sessionID/finish` read the record without a lock, so two devices (or a retry after a lost response) both read `prUrl === null`, both pushed and both ran `gh pr create`/`glab mr create`; the loser got "already exists", `createPullRequest` collapsed every failure (duplicate, auth, missing CLI, timeout) to `null`, and the route persisted the compare URL. Because `record.prUrl ??` and `pr_url = COALESCE(@prUrl, pr_url)` keep the first non-null forever, that fallback then beat the real PR permanently. Coalesce the whole operation per session with an in-flight promise registered before the first await (rule 12) and re-read the record after acquiring the slot; when the provider's create fails, look the existing resource up (`gh pr list --head <branch> --state all --json url`, `glab mr list --source-branch <branch> --output json`) with the same bounded runner/env before returning null; persist only a provider-returned URL and keep persistence monotonic (`pushed` never downgraded, first real URL wins); treat a stored value equal to `pullRequestUrl(remoteUrl, branch, baseRef)` as a legacy, non-authoritative compare URL and replace it on the next finish. A fallback/compare URL may be returned in the response, never stored as if it were the real object.

### Aggregate deletion rules (#188)

27. **Deleting an aggregate releases the child lifecycles it can enumerate before the folder disappears, and never races in-flight work.** `DELETE /workspaces/:id` removed isolated worktrees and previews but never stopped the managed dev-server PTY, forgot goal runs, dropped the workspace run config or paused scheduled tasks, so a PTY kept running inside a folder that had just been deleted and tasks kept firing at a missing directory. Release children in dependency order: **first await an in-flight finish** (the operation still uses the worktree; deleting the branch between commit and push loses the push), await the goal cleanup, await the preview forget (which itself waits for an in-flight tunnel start and kills the child it produced), stop the managed run with the strongest primitive that also adopts an orphan by title, then remove the worktree/record. This applies to **base-folder sessions too**, not only isolated records; isolated records are enumerated from the store (authoritative), while the base-folder list is best effort when opencode is unreachable (logged, the row/folder still go). A release is registered synchronously as one single-flight entry per session in an app-scoped `Map<sessionID, { promise, directory, repoPath }>` before it awaits the finish map: overlapping releases (the DELETE route plus `session.deleted`, two clients) share that promise instead of clearing the marker while the first is still removing the worktree, a directory supplied by a later caller is recorded (and `runs.stop` re-runs idempotently after the shared release when the first had none), and the entry is removed in `finally` only when it is still the same one. `finish` checks that map synchronously before registering and answers `404 not_found` (the session is being removed, not a retryable `workspace_busy`) instead of committing/pushing into the worktree. Cleanup has two policies. The session DELETE (`bestEffort: false`) rethrows a storage failure so `app.onError` answers `503 storage_unavailable` while the record/port row survives for a retry (its upstream session is already gone, so `200` would leave no retry path). Aggregate deletion and the out-of-band `session.deleted` event are best effort: once the workspace row is gone nothing can retry it, so goals/preview/run/record failures are logged and the remaining children still release instead of turning a half-deleted aggregate into a `503`. `worktrees.remove` is itself best effort and git-status-silent (`git worktree remove`/`branch -D`/`prune` run through the non-throwing runner), so a branch or directory it fails to drop is a logged residual, never a failed delete. Pause every scheduled task aimed at the folder through the scheduler's own serialized `pauseTask` **before the active-session guard**: `pauseTask` waits for an in-flight fire, so the guard then sees the session that fire created (a guard-first order would pass while the fire's create is still in flight and delete the folder under it). The scheduler also revalidates `getWorkspaceByPath` inside `processDue`, `taskRunNow` and boot, persisting `paused=true` and answering `409 task_paused` instead of firing into a removed folder. A refused destructive delete (`409 workspace_busy` or `502 busy_check_failed`) resumes exactly the tasks this request unpaused (`resumeTask` recomputes a strictly future slot), so a failed delete does not silently disable the schedule. **Remove the workspace row (with its run config) early, before releasing children**: the synchronous delete closes the delete-vs-create window. A create that already passed its workspace lookup must re-read the row synchronously immediately before inserting (normal and timeout-recovery paths) and roll back — delete the known session, remove the worktree, answer `409 workspace_busy` — when it is gone; otherwise a record would reference a deleted workspace and its worktree would leak. When the workspace folder was removed too (`deleteFiles=1`), git cannot reach the deleted repository, so the rollback must also remove the worktree directory directly (the path comes from `worktreeDir`); reconcile only walks existing workspaces and would never find it. A **standard** (non-isolated) create has no record to roll back, so it re-reads the row as soon as opencode returns, awaits the bounded upstream session `DELETE` (a failure is logged) and then answers `409 workspace_busy`. Because the row goes first, re-list the isolated records **after** removing it (a record inserted during an earlier guard await is only visible then), and pass the repo path explicitly to the child release (the usual workspace lookup is gone). The row is removed before the folder on every delete; only `deleteFiles=1` removes the folder, and if that fails the files remain without a registration. The destructive variant first verifies that no session is active across every directory it will remove, and fails closed (`502`) when it cannot confirm; path refusals (`403 outside_root`) must come before any cleanup (and before pausing tasks) so a refused request never touches a child.

### Scheduler patch rules (#189)

28. **Never persist a full record built from a read that crossed an await.** `PATCH /api/scheduled-tasks/:id` read the task, awaited the model-catalog check (up to ~10 s) and then wrote `{ ...snapshot, ...patch }` with a full `INSERT OR REPLACE` outside the scheduler's per-task chain: a fire that advanced `lastRunAt`/`nextRunAt` in that window was overwritten (the next tick could fire the same slot again), a concurrent pause was lost, and a task deleted meanwhile was resurrected by the write. A route may read an entity to validate the request and compute derived fields, but the write must run **inside the entity's serialization chain** (`updateTask` → `runExclusive`), **re-read the live record immediately before persisting**, and write **only the fields the body actually changed**. When the row is gone, answer `404` — never re-create it. Lifecycle fields (`paused`, `lastRunAt`, `createdAt`) are never part of a general edit patch: they have their own serialized operations (`pauseTask`/`resumeTask`, the fire path). Network-bound validation (catalog, directory) stays outside the chain so a slow upstream can never block fires; mixed bodies apply the edit first, then the lifecycle transition.

### Preview port reservation rules (#195)

29. **A uniqueness invariant needs a write that cannot delete the conflicting row, and its test must hit the real constraint.** `preview_ports.port` was `UNIQUE` and `portFor` retried on `SQLITE_CONSTRAINT_UNIQUE`, but the write was `INSERT OR REPLACE`: when two sessions raced for the same candidate, the loser deleted the winner's row and never raised, so the retry was dead code and a session silently lost its reserved port. Enforce uniqueness with a statement that can only add or keep a row — `INSERT … ON CONFLICT(<entity id>) DO NOTHING` plus an affected-row check that returns the **persisted** row when `changes === 0`, never the value the attempt picked. A conflict on the other unique key must be allowed to raise the real constraint, and the retry must match that exact code (`isUniqueConstraint`), not every `SQLITE_CONSTRAINT*`, or unrelated failures are retried or masked. Test the statement against the real store (force the race by hiding the winner from the allocation read), never an injected throw: a synthetic error keeps passing after the SQL regresses to a destructive upsert.

### Tooling rules (2026-10-28: `GIT_DIR` leak into a linked worktree)

30. **Never run git-spawning gates with `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE` set, and verify HEAD right after committing in a linked worktree.** The server suite shells out to `git` (temp repos in `git-async.test.ts` set a local `Test` identity and commit `-m init`). Run once with `GIT_DIR` pointing at a linked worktree, every `git init/config/add/commit` in every temp repo targeted the real branch instead: the temp `README.md` (`"init\n"`) plus deletions of everything else committed as `init` authored by `Test`, twice, and the repo-local identity was clobbered to `Test` (later commits inherited the wrong author). Mitigations: run gates with those variables explicitly scrubbed (`env -u GIT_DIR -u GIT_WORK_TREE -u GIT_INDEX_FILE`); assert `git log --oneline -1` shows the intended message immediately after committing; keep repo identity out of test reach (tests set identity only inside their temp dirs, but a redirected `git config` writes the real repo config — restore it). A commit whose message is not the one passed, or a `git status` showing the tree replaced by untracked files, means the index/HEAD moved under you: stop, `git reset --hard` to the pushed tip, re-apply from a backup, and find the leak before retrying — never push a suspect HEAD (the pre-push gate failing is what saved the remote here).

31. **Listen before reconciling: boot serves first, maintenance settles in the background.** Awaiting an unbounded maintenance pass (`reconcileWorktrees`: N×2×60 s of git worst case) before `serve()` holds the healthcheck past its start period until the orchestrator restart-loops the container (#199). Build the app and listen first, run the pass in the background with a slow-pass budget that only warns (12 s), and split the probe: liveness (`/api/health` 200 while the store answers) responds immediately, readiness (`ready`) flips when the pass settles — success and warned failure alike, or one bad git pass pins the container unhealthy forever. The volume-health gate and quarantine semantics do not move (rule 11). Test the helper, not the entry point: `launchBackgroundReconcile` takes an injectable pass, contains failures (its `settled` never rejects), and evaluates the pass before notifying — `onSettled?.(await pass())` silently skips the pass itself when no observer is registered.

### Native worklet rules (2026-10-28: board drag crash)

32. **Respect the JS ↔ UI runtime boundary in Reanimated worklets.** A gesture callback (`onStart`/`onUpdate`/`onEnd`/`onFinalize`) runs on the UI runtime: any helper it calls synchronously must itself be a worklet (the `"worklet"` directive), or the call throws `Tried to synchronously call a Remote Function` and closes the app. `runOnJS`/`scheduleOnRN` only accept a function **defined on the RN runtime** (a captured function reference serialized as a `RemoteFunction`); an arrow created inside the worklet throws `[Worklets] Locally defined function passed to scheduleOnRN`. Keep the latest-callback pattern, but put the ref behind a stable JS callback — never capture the ref object itself in a worklet, because it is serialized, frozen and warns on every later `current` write (`Tried to modify key 'current' of an object which has already been passed to a worklet`). These are device-only failures Jest cannot reach: guard the source in `apps/mobile/test/app-guards.test.ts` and verify the gesture on a device before closing.

## Checklist for a new mutating operation

- [ ] Request bounded by a deadline (or an explicit, justified override).
- [ ] A paginated read on a deadline path takes the signal, checks it before every page and passes it to the fetch; it never joins an in-flight shared fetch it cannot abort. Detached cleanup after the response gets its own budget instead of the already-expired request signal, and a resource-removal step is never cancelled mid-flight (that leaks the resource). A release skipped at the cleanup cap still releases its goal/preview/PTY lifecycles, and keeps the record and worktree together for manual cleanup.
- [ ] Local `busy`/optimistic state is reset on **every** outcome (success, error, timeout, unmount).
- [ ] Text/inputs edited during the operation survive the response.
- [ ] Timeout surfaced as "unknown / may have succeeded", not a failure.
- [ ] Route catch-alls rethrow storage failures (`isStorageError`) to the single `onError` `503 storage_unavailable` before typed fallbacks and before any rollback/cleanup.
- [ ] A non-idempotent mutation is never auto-retried (unless a persisted marker proves it did not land first — ADR-32).
- [ ] If a confirmation channel exists, wire it and let it beat a later timeout.
- [ ] Created/partial resources are removed on failure and unmount.
- [ ] A non-idempotent create that times out reconciles its persisted marker (fresh, directory-scoped) before any rollback; a duplicate reconcile adopts the record the first one persisted only when its `path` and `workspaceID` match this attempt (a real retry uses a new token/worktree), otherwise the conflict is rethrown; an unconfirmed resource is preserved (quarantine), never deleted; when the rollback loses the repo folder (`deleteFiles=1`), the worktree directory is removed directly.
- [ ] In-flight guard uses a ref, not state alone.
- [ ] Concurrent identical mutations coalesce server-side (no duplicate PTY, process or record).
- [ ] A provider create that can answer "already exists" (PR/MR, remote object, branch) coalesces per entity and reconciles against the provider before reporting failure; a fallback/compare URL is returned, never persisted as the real value, and stored real values/pushed flags are monotonic.
- [ ] Resource growth (logs, memory) is bounded and exhaustion is surfaced to clients.
- [ ] Destructive cleanup paths confirm storage health first and quarantine rather than delete irreplaceable data; a destructive delete refuses while a child is active and fails closed when the busy check cannot be evaluated.
- [ ] Deleting an aggregate waits for in-flight children (finish, preview start, run start), refuses a child mutation that starts after its release began (single-flight release map → `404 not_found`; overlapping releases join the first), releases every child lifecycle for isolated **and** base-folder sessions (the latter best effort when upstream cannot be listed), and pauses dependent schedulers **before** the active-session guard so an in-flight fire's session is seen; a refused delete (`409`/`502`) resumes only the tasks it paused, and a cleanup failure after the row removal is logged instead of answering `503`; if the parent row is removed first to close create races, the create re-checks it before inserting and a fresh child list runs after the removal.
- [ ] A partial update writes only the changed fields over a fresh read inside the entity's serialization chain; it never persists a snapshot taken before an await, never resurrects a deleted row, and leaves lifecycle fields to their own operations.
- [ ] A uniqueness constraint is enforced by a statement that cannot delete the conflicting row (`ON CONFLICT(<identity>) DO NOTHING` + return the persisted row); the retry matches the exact constraint code, and the test provokes the real conflict against the real store, never an injected error.
- [ ] A dropped-privilege child gets a cleared environment + allowlist, not just a different uid; every execution path uses the same dropper (a new PTY path defaults to the engine uid); engine DB/config/log are owner-only.
- [ ] A schema change is a new ordered migration in `apps/server/src/migrations.ts`, never an edited shipped version or a boot-time `CREATE TABLE IF NOT EXISTS`; a newer `user_version` is refused with the restore pointer.
- [ ] Identity comes from a stable client-owned key with a unique constraint, not a mutable display label; re-login keeps the label, sign-out keeps the key, and a concurrent duplicate is reconciled by re-reading the winner.
- [ ] Native gesture helpers called from a worklet carry the `"worklet"` directive, `runOnJS`/`scheduleOnRN` targets are defined on the JS runtime, and no ref written after render is captured by a worklet (guards in `apps/mobile/test/app-guards.test.ts`).
- [ ] Tests cover: lost response, timeout, slow success, double submit, unmount mid-flight.

## Already-established patterns (reuse, don't reinvent)

- `client-core` `RequestTimeoutError` + `timeoutMs` (PR #62).
- BFF `fetchOpencode`/`OpencodeTimeoutError` + `OPENCODE_TIMEOUT_MS`: one bounded entry point for internal opencode calls, mapped to `504 opencode_timeout` (#75).
- Synchronous send lock in both composers: `inFlight`/`startingSideQuestionRef` refs, set before the first `await` (#72; `inFlight` also backs the pending-send ghost, #125).
- Web composer delivery reconciliation via `queryKeys.messages` and the per-send marker persisted in the prompt `metadata`: `createDeliveryMarker` / `deliveryMetadata` / `deliveryMarkerOf` in `client-core` (#71; replaces the PR #63 text + time heuristic).
- Worktree reconciliation volume gate + quarantine: `reconcileWorktrees` requires `VOLUME_SENTINEL` or a live recorded path before dropping records, and `manager.quarantine` renames orphan worktrees (branch kept, git admin pruned) instead of deleting them (#79).
- Reconnect reconciliation: `invalidateOnReconnect`, `syncPending` for permissions/forms, `server.connected`.
- **Bounded retry with marker reconciliation** (`apps/server/src/retry.ts`, ADR-32): idempotent opencode calls retry transient statuses/network failures with incremental backoff (×2, capped, jitter, bounded attempts; timeouts only where the caller can reconcile). Non-idempotent calls pass a `reconcile` callback that looks up their persisted marker (`masterhand.goal.*`, `masterhand.delivery` in prompt metadata, session `metadata` for creates) and resolves the operation instead of replaying when it already landed; a lookup that itself fails aborts the retry with `AmbiguousMutationError` (the outcome is unknown, so nothing is replayed — fail closed). Exhaustion rethrows the last response/error; the goal maps it to a resumable `error` with the attempt count. Do not add a second retry loop around a caller that already uses the engine, and do not retry timeouts on unreconciled paths.
- **Storage failures bypass route catch-alls (#191):** `goalFailure`, `schedulerFailure`, the isolated-create catch and the run/preview catches call `isStorageError(error)` first and `throw error`, so `app.onError` answers the shared `503 storage_unavailable`. Infrastructure is not a domain failure: a `SQLITE_FULL` while persisting the isolation record leaves the worktree and session intact (no `DELETE`, no `remove`), and non-storage errors keep their exact status/body (`502 goal_failed`/`scheduler_failed`/`opencode_unreachable`, `500 isolation_failed`/`run_failed`, `504 opencode_timeout`).
- **Goal Mode phase recovery** (`apps/server/src/goal.ts`, ADR-33): a failed turn (`session.execution.failed`) re-drives its phase up to 3 times with 2 s/4 s/8 s delays; opencode's own `session.retry.scheduled` only updates the run note; a missing completion marker gets **one** corrective nudge then errors; a watchdog reconciles lost `session.idle` events by checking `/api/session/active` and reprocessing the last assistant message (idempotent through the per-phase baseline); `reconcileOnBoot` turns in-flight runs into `paused` (never auto-resume); the main session's deletion drops the run and an awaited internal session's deletion fails it. Tests cover 429 → backoff → success, ambiguous timeout reconciled, lost idle, restart and cap/resume.
- **Internal sessions are hidden by MasterHand, never by an upstream field**: the pinned opencode (v2.0.6) silently drops `parentID` on session create (verified in its schema; upstream added it after 2.0.6), so Goal Mode's critic/judge sessions were created as roots and listed in the sidebar. The BFF tags each internal session with a stable metadata role (`masterhand.goal.internal`), `GET /workspaces/:id/sessions` annotates it (`goalRole`, falling back to the run store and the legacy unique-marker prefix), `rootSessions` filters the annotation, and `forget`/cancel/new-run delete the sessions explicitly because upstream cascades nothing. The same quirk invalidates **marker reconciliation scoped by `parentID`**: the create-reconcile lookup must search by directory (the created session is a root), or a lost response replays the create and duplicates the internal session — proven red (two critics) then green. **Never assume an optional upstream field is honored because the SDK types accept it** — verify against the pinned version and keep a MasterHand-owned marker for anything the UI or the retry engine relies on (the E2E mock now drops `parentID` exactly like the pinned server: `Goal critic` listed = red).
- Cache merge to avoid event/poll races: `mergeStatuses`, `mergeLiveMessages`, `reconcilePermissions`, `reconcileForms`.
- Event-hub stall watchdog: `parseSseStream`'s `onActivity` reports raw chunks (heartbeats/comments included), the hub aborts/reconnects past `stallMs` (opencode heartbeats every 15 s, default window 45 s) and pushes `hub.connected`/`hub.disconnected` downstream so clients refresh `/api/status` immediately (#76).
- SSE watchdog + reconnect (`createEventStream`) and the BFF heartbeat.
- Open-entity reconciliation by list diff: keep the ids of the previous list snapshot and close/replace the open entity only when it **was present before and disappeared** from a fresh fetch (web open session on `session.deleted`, #69). Never close on an absent id that was never seen: a just-created entity or a stale in-flight response must not be dropped.
- Bounded per-client SSE queue: `/api/events` writes through one serialized drain loop and drops a client that falls more than `MAX_SSE_QUEUE` frames behind, instead of forking an unbounded promise/string chain (#83).
- **SSE write-failure teardown (#190):** a rejected `writeSSE` means the transport is gone (reset socket, half-open connection), so the drain loop tears the client down right there — clear the queue, unsubscribe, abort, never retry or re-drain — instead of swallowing the error and waiting for the abort/keepalive path. Without it `closed` stays false, the hub subscription leaks, and every later frame is silently lost while the drain keeps failing. The client reconnects (SSE has no replay) and reconciles, the same contract as the #83 overflow drop. Failure class E (partial failure leaves a resource orphaned): a dead transport held its subscription forever.
- **SSE byte budget + shared serialization (#196):** the frame-count cap alone allows 1024 × ~1 MB ≈ 1 GB of queued frames per stalled client against a 1 GB container, so every `/api/events` client also owns a byte budget (`MAX_SSE_BYTES` = 4 MB, injectable as `sseBytesMax`): over budget it drops + aborts under the same reconnect-and-reconcile contract as #83/#190. Each hub emission is serialized once and the string shared across every subscriber (the hub notifies synchronously, so the memo always hits; only the latest emission is retained). Oversized `tool.success` outputs are deliberately NOT truncated: frames stay verbatim so clients keep rendering full outputs, the authoritative copy stays in the opencode message history the clients refetch on reconnect, and truncating would break the full-snapshot (`goal.updated`/`board.updated`) pattern reconnect relies on (rule 13).
- Terminal startup state: `/api/status` resolves the shell on **every** outcome — success → app, 401 → login, transport error → login + banner, any other HTTP error → retry screen (`statusFailed`) — so a 5xx can never leave "Loading…" forever (#81).
- Session-create reconciliation by marker: `createSession` sends `marker`, the BFF persists it as opencode session metadata (`masterhand.create`) and returns it from the list; on a timeout/504 the client walks the list (bounded: three attempts) and opens the marked session instead of reporting a failure (#66). No blind retry.
- **Isolated-create reconciliation before rollback (#185):** the BFF's own `OPENCODE_TIMEOUT_MS` on an isolated create is ambiguous too. The route keeps the fresh worktree, lists that directory fresh (`fetchSessionsInDirectory`, never the 5 s `sessionsInDirectory` cache), matches only the same `masterhand.create` marker and, on a hit, persists the same `isolated_sessions` record before the best-effort preview/workspace guards and answers `201 { session, isolation }`; a duplicate reconcile that hits the record's primary key defensively adopts the persisted row (`getIsolatedSession`) only when its `path` and `workspaceID` equal this attempt's, otherwise the conflict is rethrown so the #191 storage mapping answers `503 storage_unavailable`; a real retry uses a new token/worktree, so this is a guard, not a reachable normal path. Without the marker it answers `504 opencode_timeout` and leaves the worktree (plus any unknown session) to `reconcileWorktrees` quarantine (#79); no record exists, so the worktree is not aggregated and only the marker path can recover it. A non-timeout failure still deletes a known session and rolls the worktree back. Tests cover marker found, marker absent, the recovered record surviving `reconcileWorktrees` + `GET /workspaces/:id/sessions`, the non-timeout rollback, the `deleteFiles=1` directory fallback and the defensive duplicate-reconcile conflict (matching path/workspaceID accepted, a mismatch rethrown).
- Auto-accept retry: bounded attempts with backoff (`AUTO_ACCEPT_MAX_ATTEMPTS`/`AUTO_ACCEPT_RETRY_DELAYS_MS`, web + mobile), tracked per permission in a pending set that `permission.replied` clears; after the cap the session is never left silently blocked — the inline card plus an actionable banner let the user answer manually (#70).
- Coalesced non-idempotent starts: `RunManager.start` keeps a per-session in-flight promise, so two Start taps (or devices) share one PTY instead of racing into duplicate dev servers; `stop`/`forget` wait for the in-flight create before acting (#84).
- Out-of-band entity cleanup: the BFF hub treats `session.deleted` as authoritative and releases the session's managed resources (quick tunnel, PTY, reserved port, worktree record/branch) even when no route ran (#85). Startup reaps orphaned `cloudflared` PIDs recorded at spawn time, killing only PIDs still confirmed to be cloudflared (PID-reuse guard).
- Bounded transition + liveness polling: `transitionPollInterval` polls `starting` at 1.5 s up to `STARTING_TIMEOUT_MS` (then the UI shows a timeout) and `running` at 5 s so a run/tunnel that dies on its own flips to `stopped`/`error` with a visible notice instead of a stale "running" (#89, #73).
- Ambiguous answer reconciliation: `respondPermission`/`respondForm`/`cancelForm` treat `RequestTimeoutError`/504 as "may have applied", reconcile against `GET /permission` / `GET /form` before reporting, and only invite a retry when the request is provably still pending — with ref in-flight guards so a same-tick double click cannot double-answer (#67).
- Long-operation budget + record reconciliation: `finish` uses `FINISH_TIMEOUT_MS` (240 s) instead of the interactive deadline, reconciles a lost response against the isolated-session record (`finishResultFromIsolation`), and the server never re-creates a PR when `pr_url` is already recorded, so a retry is safe (#65).
- Degradation ladder: `app.onError` maps SQLite errors to `503 storage_unavailable` (everything else to a logged `500 internal_error`), advisory writes are wrapped and logged once, and `/api/status` carries `storage.ok`/`storage.low` for client banners (#86, #88). SQLite runs `quick_check` at boot, `VACUUM INTO` backs it up online (`npm run backup` / `dist/backup.js`, `docs/runbooks/backups.md`), and unexpected process failures log + exit deliberately (#80, #88).
- Async external work: `runGitCommand` + `spawnResult` (worktrees.ts) run every git/`gh`/`glab` call through `spawn` with a per-call timeout, process-group kill and an injectable runner; `createWorkspaceDir`/`removeWorkspaceDir` use `fs/promises` and `preview.available()` probes `cloudflared` without `spawnSync` (#77).
- Guarded branch mutations: `POST /workspaces/:id/branches` and `/checkout` validate the ref name, refuse while any workspace session is busy (fresh list vs `/api/session/active`, fail-closed `502 busy_check_failed`), reject a dirty tree on checkout (`409 dirty_worktree`) and answer a git deadline as `504 git_timeout` — the client (`branchErrorMessage`, `BRANCH_TIMEOUT_MS`) frames it as "may have applied", refetches the branch list and never auto-retries (#94).
- Mobile secure-storage resilience: bootstrap catches SecureStore failures (login screen with a storage-specific message, never a permanent spinner), login separates authentication from persistence (the session stays usable in memory with a banner when it cannot be saved) and `saveSessionPreferences` serializes its read-modify-write queue so concurrent saves cannot clobber each other, keeping the chain alive after a rejected write (#82).
- Pending-send ghost with marker reconciliation: `usePendingSend` (client-core) owns the plain-prompt state (`begin` on submit, `fail` on a hard error) and clears it only when the persisted history shows the send's marker; the composer releases when the ghost clears, so a lost response resolves without a deadline wait and the real bubble and ghost never coexist. Slash commands keep button-only feedback; an ambiguous timeout keeps reconciling and is never auto-retried (#125).
- **Per-worker E2E harness (#175, supersedes the shared-scratch pattern):** one mock + one BFF per Playwright worker, spawned by the worker-scoped `harness` fixture (`e2e/fixtures.ts`) with `node --import tsx` (a single process, so SIGTERM reaches the server), health-polled before the first spec and killed with the worker. **Every port, scratch dir and the cloudflared die file derive from the worker index** (`testInfo.parallelIndex`/`TEST_PARALLEL_INDEX` in `e2e/paths.ts`, pure functions — never the clock or the pid, because the config/test module is evaluated in the runner *and* in every worker); `baseURL` is overridden per worker, so `page.goto("/")` and relative `page.request` can never reach another worker's BFF, and the process-global `/e2e/*` mock controls are global only *within* one worker (a spec that arms one resets it in `afterEach` so a failure cannot poison later specs of the same worker). `globalSetup` builds the web bundle once per run — the shortened `VITE_REQUEST_TIMEOUT_MS`/`VITE_FINISH_TIMEOUT_MS` are build-time, so losing them there silently slows the stalled-send/lost-finish specs — and wipes the scratch root. `cleanup-ports.mjs` frees the whole derived block (`4097..4104`/`8788..8795`) and wipes the scratch root before every run, so a killed run (count or workers unknown) is reclaimed. Locked by `scripts/e2e-harness.test.mjs`; the old shared harness measured w2 98/103 and w4 95/103 (2026-10-17) — cross-worker collisions, not CPU — which is why the fix is isolation, never a retry knob.
- Provider credentials from settings: `connectIntegrationKey`/`removeCredential`/`activateCredential` go through the allowlisted `/api/oc/*` proxy; the UI shows an ambiguity message on a timeout (never auto-retry), refreshes the integration list to reconcile, and treats keys as write-only (never pre-filled, echoed, logged or stored client-side) (#128).
- Custom provider definition writes are **idempotent upserts by id** (atomic temp-file + rename, serialized per BFF instance, unknown config entries preserved) and a malformed file is **never overwritten**; connecting the API key after a write is a best-effort, bounded retry of opencode's `connect/key` where `404` means "not registered yet" and created nothing, so a retry is safe, and a failed connect never fails the create — the UI offers Connect to reconcile (ADR-30).
- **The owned config file is shared: every write preserves all top-level keys** (ADR-34). It now carries opencode's `websearch` selection next to `providers`, so the store reads the whole document and writes unknown keys back verbatim — a provider upsert must never drop another feature's section. The web search default is **seeded, never enforced**: boot writes `websearch.provider = "tinyfish"` only when the key is absent, and `GET /api/websearch` repeats the seed lazily (the E2E harness wipes its scratch dir *after* the servers boot, and a file recreated under a running BFF must still get the default); a present value — hand-edited included — and a malformed file are never overwritten. The seed exists because opencode's first-search provider form (`metadata.kind = "websearch.provider"`) is **not rendered by MasterHand clients** (only `question` forms are): an unseeded install would make the agent's web search time out as "cancelled". Rule of thumb: when a feature depends on an upstream prompt MasterHand cannot show, MasterHand pre-answers it in the config it owns.
- Custom provider **model discovery** (`POST /api/providers/custom/models`) is a bounded (10 s `AbortSignal.timeout`), injectable outbound request to the user-entered base URL's `/models`; it is read-only, the transient key is only forwarded upstream (never logged or persisted) and it is the only way to populate the dialog (manual model entry was removed), so a failure shows `This provider does not expose models.` and keeps Create disabled until the list loads. The dialog's debounced auto-run uses a monotonic request-id ref so a late response cannot overwrite a newer one, and stays silent while no key is entered (a keyless provider must not flash an auth error).
- Shared cross-platform token modules: color themes (`palettes.ts`: ids, labels, per-mode sets, paper fallback) and syntax highlighting (`highlight.ts`: path/fence detection, six token kinds) live in `client-core` as pure data/functions with one platform renderer each, so 13 themes × 2 modes and the token grammar cannot drift between CSS and native (#124, #123).
- Android system bars follow the app theme at runtime (`ThemedSystemBars` over `expo-navigation-bar`, best-effort and never-throwing); on forced edge-to-edge the bar is transparent and the themed canvas behind it does the visual work (#118).
- **Mobile chat honors the same mutation contracts as web.** The React Native `BranchPicker` frames checkout/create timeouts as "may have applied", refetches the branch list and never auto-retries (#94); `ChatScreen.finish` reconciles a lost response against the isolated-session record with the same bounded polls (`finishResultFromIsolation`, #65); and `Composer.stop` reports ambiguity instead of failing silently. A new client must port these paths, not reimplement them.
- **Derive every markdown color from the active theme.** The mobile chat hardcoded the renderer's `colorScheme="dark"` and layered the library's dark preset over light surfaces, which left bold text and inline code unreadable in light mode and fenced blocks half-styled. The style factory now resolves every run (body/strong/em/inline/fence) from the palette and the scheme follows the theme — a new markdown element must add its colors there, never rely on a preset.
- **Idempotent positional mutations for ordered collections** (board, #164): when the mutation is an absolute assignment (`(columnID, position)`) rather than a relative move, make it replay-safe by construction — client-generated ids with `INSERT … ON CONFLICT(id) DO NOTHING` (a replay returns the existing row, never overwrites an edit), sequential reindexing in a transaction on every affected scope, idempotent deletes, and a full-snapshot SSE frame (`board.updated`, like `goal.updated`) with reconnect refetch. The client commits optimistically then `PATCH`es the absolute position; on failure it refetches and toasts — no blind retry loop, no marker lookup (ADR-32 does not apply because there is nothing non-idempotent to reconcile). Deleting the parent scope removes its children in the same transaction (column → cards; workspace → board). Scope membership is validated at the trust boundary: a move into another scope's container answers `409` and leaves the source untouched (a card never changes workspace through a column move), and the frame's scope resolves with an O(1) lookup, never a full scan per mutation.
- **Scheduled non-idempotent fires (scheduler)** (#147, ADR-36): every task transition — tick pass, opencode event, "Run now" — is serialized through a per-task in-flight chain (rule 12, like `RunManager.start`), so two devices or a retry can never double-fire a task; run-now (`source: "manual"`) goes through the same serialized path, so double taps coalesce into one run. A fire = create session + pin model + prompt, all non-idempotent, so the retry engine reconciles persisted `masterhand.scheduler` markers (`<taskId>#<runId>#create` / `#prompt`) — **scoped by directory, not `parentID`**, because the pinned opencode drops `parentID` on create — and an unresolved ambiguity marks the run `failed` instead of replaying blind (the session created before the failure stays, nothing is cleaned up destructively). Overlap is enqueue, never stack: a due fire while a run is active records **one** coalesced `queued` run that fires right after the active run settles, and a task paused or deleted meanwhile turns it `skipped`. Boot reconciliation is explicit and never a guess: `firing → interrupted`, `queued → skipped`, no auto-resume, and `nextRunAt` recomputed anchored on the missed slot — so missed slots and downtime are **silently skipped (no catch-up, no backlog records), never replayed**. A `running` turn self-heals by checking opencode's active sessions on ticks (the goal-watchdog pattern) instead of trusting a single terminal event.

- **Untrusted workspace repositories (#178):** `runGitCommand` keeps an allowlisted child env and `GIT_CONFIG_*` overrides; `createWorktreeManager` preflights local/worktree config and throws `unsafe_git_config` before any operation. The Docker image trusts `/workspace` only in system config; each call adds a command-scope `safe.directory` for the exact repository, because git does not match parent directories. `gh`/`glab` receive only their own token; `GIT_SSH_COMMAND`/`GIT_ASKPASS` are the explicit credential channels. Remote catch-up: hooks from husky are neutralized, not rejected.
- **Bounded bodies + failure-only limiter (#180/#181):** `bodyLimit` runs before parsing on `/api/login`, `/api/devices` (64 KiB) and `/api/oc/*` (`PROXY_BODY_LIMIT_MB`, 10 MiB default); passwords are capped at 1024 chars. The limiter checks the password first, records only failures, TTL-sweeps and LRU-bounds its key map, and logs failures without the secret.
- **Owner-only storage (#182):** `ensureDataDir` creates/chmods `0700`; SQLite is pre-created `0600` (sidecars inherit the mode); backups run under umask `077` and are chmodded `0600`; the tunnel PID file is `0600`.
- **Strict boot configuration (#183):** `boolFromEnv` accepts `true/false`, `1/0`, `yes/no`, `on/off` case-insensitively and aborts on anything else; production requires 32-byte non-placeholder `MASTERHAND_PASSWORD`/`SESSION_SECRET`; `COOKIE_SECURE=false` warns at boot.
- **Provider-discovery target guard (#184):** literal and DNS-resolved loopback/unspecified/link-local/metadata/multicast/reserved addresses are `invalid_base_url` before the request; private LAN stays allowed (ADR-30) and loopback only with `PROVIDERS_ALLOW_LOOPBACK=true` (metadata stays blocked even then); one deadline covers lookup + fetch.
- **Path/ref edges and persisted input caps (#209/#210):** `decodeURIComponent` failures are `400 invalid_path`; `headBranch` output and every `baseRef` pass `isValidBranchName` before reaching argv; scheduler `name`/`prompt` are capped at 200/8000 with `invalid_name`/`invalid_prompt` on create and patch.
- **Managed-run isolation + client proxy allowlist (#179, ADR-22/23/37):** `MANAGED_RUN_LAUNCHER=/usr/local/bin/agent-exec` makes the run PTY execute `agent-exec --exec <command> <args>` — the helper drops to `agent` (uid 1001/gid 1000, no supplementary groups), clears the inherited environment (allowlist: `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `TERM`, `LANG`, `TMPDIR`, validated `PORT`), and execs the argv verbatim (no shell); the UI keeps the user's command/args and `agent-exec` is rejected as a run command. `/api/oc/*` is a method-exact allowlist of the client surface (`client-core`); everything else answers `404 not_found` before this proxy reads the body (bodyLimit may answer 413 first) or an upstream call is made, encoded slashes are refused, and BFF-owned `callOpencode` paths are unaffected. Engine data/config/log are owner-only at every container start; the BFF's provider config is `0600`. Verified at runtime on the dev stack (uid/env/kill/read denial, PTY proxy 404 vs model 200) and by `deploy/agent-exec-drill.sh`; #216/#217 are residual follow-ups.
- **Forward-only SQLite migrations (#186):** `apps/server/src/migrations.ts` owns every DDL statement in the frozen v1 baseline; `runMigrations` reads `PRAGMA user_version`, applies only pending versions in one transaction (`statements` then `user_version = version`), skips applied versions on reopen, refuses a newer schema, and closes the database with the restore pointer when a migration fails. `createSqliteStore` runs it after the open/`quick_check` phase and before the first `db.prepare`, so a new column ships as v2 (never a `CREATE TABLE IF NOT EXISTS` edit) and an existing installation upgrades instead of breaking boot. The corrupt/non-SQLite open path and migration failures both name `docs/runbooks/backups.md`.
- **Stable device identity (#193):** migration v2 adds `devices.install_id` plus `UNIQUE(install_id)` (NULLs stay distinct), `POST /api/devices` dedupes through `store.getByInstallID`, keeps the existing label on re-login, and re-reads the winner on a unique-index race; callers without an `installID` keep a new row per login. Mobile persists the id under `masterhand.installID` (never cleared on sign-out), coalesces concurrent `getOrCreateInstallID()` calls and falls back to an in-memory id when SecureStore fails, so login never breaks (#82). The display name is a label only.
- **Credentials from integration connections (#216):** `client.api.credentials()` derives the list from the allowlisted `GET /api/integration` connections (`credentialsFromIntegrations` in `client-core`) instead of calling `GET /api/credential`, which the pinned 2.0.6 answers with `404` (and which the proxy never allowlisted). `active` is approximated as the first credential connection per integration — the store exposes no active flag there — while disconnect/activate keep their existing (allowlisted, upstream-supported) routes. The E2E mock no longer implements the missing route, so the suite is exactly as strict as production. Keeping the derived shape (`{ id, integrationID, label, active }`, no secret value) means the UI renders rows from connections exactly as before.
- **Catalog secret stripping (#217):** `createOpencodeProxy` deep-strips apiKey-like keys (`/^api[_-]?key$/i`, any depth) from proxied `GET /api/model`, `/api/model/default` and `/api/provider` responses while keeping sibling keys (`baseURL`, …). Verified against the pinned 2.0.6: a custom provider's `settings.apiKey` echoes verbatim through both `/api/provider` and `/api/model` (the built-in provider only serves the `"public"` placeholder, and connected keys stay in the credential store — but any configured value leaks). Both test mocks serve a realistic fake key so the suite catches a regression; clients only read catalog identity fields, so the shrink breaks nothing.
- **Project plugin discovery disabled (#218):** Compose sets `OPENCODE_CONFIG_PROJECT_DISABLE=true` on the opencode service (and the native `dev.mjs` fallback defaults it too). Verified against the pinned 2.0.6 source (`server-process.ts` → `ServerOptions.config.project` → config discovery, instruction discovery and the config plugin source) and at runtime: a marker plugin under `<workspace>/.opencode/plugin/` executed on session creation without the flag (its top-level code ran even though the shape check failed it) and never loaded with the flag. Explicit config (`OPENCODE_CONFIG`/`OPENCODE_CONFIG_CONTENT`) still applies, so the shell dropper and MasterHand-owned providers are unaffected. Residual: a workspace's own `AGENTS.md` is no longer auto-injected (the per-session `masterhand.workspace` instruction still pins the directory); global plugins/`~/.config` still load by design.
- **Delete-path abort channels (#225):** the C20 budget aborted only its own controller, so after a `504 delete_timeout` the base-folder `fetchSessionsInDirectory` had no signal and could keep paginating up to 50 upstream pages, while the remaining `worktrees.remove` calls started with the already-aborted signal (the real manager refuses to spawn git with it, so those worktrees were silently stranded even though the comment said the releases continued). The request now owns one 25 s budget that starts before the active-session guard: expiry there fails closed (`502 busy_check_failed`, nothing mutated) and covers the response, with the signal threaded through the guard's listing and active probe. The detached cleanup owns a separate 300 s admission/listing cap: the base-folder listing takes its signal (`fetchSessionsInDirectory` bypasses the shared in-flight fetch when a signal is supplied, checks it before every page and hands it to `fetchOpencode`), and no new release starts at the cap. The base listing and its releases run **concurrently** with the isolated releases, so a slow isolated phase cannot starve them; they are deliberately not tied to the response budget (a `504` caused by a slow release must not leave base sessions' PTYs/previews alive). Crucially, the cleanup signal is **not** passed to `worktrees.remove`: cancelling a git removal mid-flight deletes the isolated record while leaving the worktree behind, so the child keeps its own 60 s deadline (a git timeout remains the existing logged residual) and the release is never cancelled by the cap. A release skipped at the cap still runs its lifecycle cleanup (`goals.forget`/`preview.forget`/`runs.stop`, so no public tunnel/PTY/goal survives the folder) and keeps its record/worktree for manual cleanup (documented residual; the cap is an admission/listing cap, not a hard duration ceiling). ### Multi-server rules (2026-10-29)

33. **A saved server is a credential boundary, never a shared session.** Each profile owns its URL and its own credential: the serving origin may use the HttpOnly cookie, but every remote server must be authenticated with its own `/api/devices` token. Never copy a cookie, token or `installID`+token pair from one profile to another, and never keep remote tokens inside the profile metadata object (separate storage keys/localStorage prefix so a profile export or crash cannot leak the secret). Legacy single-server preferences (`masterhand.workspace`, `autoAcceptSessions`, `lastSeenSessions`) belong to the serving origin: migrate them only into a cookie profile after authentication, never into a remote device-token profile (and never delete them while adding a remote profile).
34. **Switching servers must unmount the previous authenticated tree.** One active `Client`, one `QueryClient` and one SSE stream at a time. Key the subtree by profile id, stop the old stream in the effect cleanup, and start from a fresh cache; a shared cache or a still-mounted component is a cross-server data leak even when every request is correctly scoped. Profile-scope the client-side preferences too (workspace, open session, auto-accept, seen markers).
35. **Session teardown is explicit and best-effort, never automatic retry.** Disconnect clears the session but keeps the profile; Remove forgets the profile and sends one idempotent `DELETE /api/devices/:id`. A timeout clears the local token, stops the UI and reports the residual revocation risk; never auto-retry a revocation or block the user on it. A 401 from a remote profile marks only that profile expired and returns to the Servers screen for re-auth — it must not log out the serving origin or another profile.
36. **CORS is bearer-only and never credentialed.** `Access-Control-Allow-Origin: *` is acceptable only while `Access-Control-Allow-Credentials` is absent and requests carry an explicit `Authorization` header. Keep the CORS headers on preflight, `401`/`429`/`5xx` and SSE, keep `requireSameOrigin` for cookie mutations, and treat `ALLOWED_ORIGINS` as the CSRF allowlist (documented as such) — expanding it must never be presented as opening CORS.
37. **Never log or render a password or device token.** Login errors show status-based copy, not the body; tokens are only in localStorage (web) / SecureStore (mobile) and in the `Authorization` header of their own server. URLs with credentials, query strings or fragments are rejected before they reach a request or a log line.

### Transport and lifecycle hardening (2026-10-29)

38. **A redirect is a credential attack surface.** Every client-core BFF request and the SSE fetch must use `redirect: "error"` (or validate `response.url`). A cross-origin request that follows a redirect to the serving origin becomes same-origin and would attach the HttpOnly cookie. Never follow redirects on API calls.
39. **Cancel must clean up the credential it caused.** A device login that resolves after the user cancelled must not be persisted or used to enter the app. Capture the issued token/device before saving, check the cancel generation immediately after it returns and again before persisting, clear the local token, and send one best-effort idempotent `DELETE /api/devices/:id`. Serialize a retry behind that cleanup so the revocation cannot invalidate the retry's new token.
40. **Never block teardown on best-effort network work.** Disconnect/Remove clear the local token and leave the app first; cookie logout/device revocation runs afterwards and reports a residual. Blocking up to 10 s left the user staring at the old server after choosing to leave it. Skip revocation when another saved profile shares the same device row.
41. **The serving origin is allowed to be plain http; remote servers are not.** The cookie profile is same-origin by definition and never sends its credential elsewhere. A LAN deployment without TLS must still boot, reload, and migrate its legacy URL. Only the exact page origin (or a one-time legacy mobile migration) may bypass the https requirement.

### Self-update rules (#134, 2026-10-29)

42. **A request that restarts the server is an ambiguous, non-idempotent mutation.** The BFF must answer `202` before the sidecar recreates the container, never retry it automatically, and keep a single attempt in flight. The client reconciles exclusively through the **post-reconnect** `GET /api/status`: compare the running version with the target, poll with a bounded deadline (5 minutes), and surface an explicit "did not apply" state instead of a spinner or a blind retry. A lost response is not proof of failure. The BFF keeps a bounded hold window after a successful trigger so a stuck pull can be retried, while the sidecar owns its own one-update guard.
43. **Back up before mutating, and fail closed.** Migrations are forward-only: the pre-update SQLite snapshot is the only safe rollback. Write it with the online backup API **before** calling the sidecar; if it fails, answer `503 backup_failed` and do not trigger. Never auto-rollback a new image (a migrated database cannot be safely used by the old binary) — the runbook restores the backup and pins the previous tag.
44. **Never expose the Docker socket to the BFF.** Docker access is root-equivalent. The opt-in sidecar is the only consumer, has no published ports, authenticates every request with a shared token, and can only pull/recreate the one `masterhand` service. A pinned image tag disables the one-click path entirely (the sidecar would re-pull the same tag); a half-configured updater fails at boot instead of advertising a button that cannot work.
45. **Auto-update is advisory and must never interrupt work.** Background checks are silent (offline, unsigned macOS, rate limits); only a downloaded desktop update prompts, and "Later" installs on quit. Desktop updates only run in packaged builds; the dev shell must never check or install. The update channel files (`latest*.yml`) ship from the same tag/release as the installers, and unsigned macOS builds are documented as not auto-updating.
